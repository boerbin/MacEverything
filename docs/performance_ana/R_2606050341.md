### Page cache 退化原因

1. **深夜 OS 内存管理**：macOS 在系统空闲时执行内存压缩和 page cache 回收。
2. **索引文件 ~1.7GB**：无活跃读取的大文件最先被回收。
3. **flush 重写不等于 page cache 填充**：flush 写入后 OS 可能不保留写入页面（write-back 后释放）。
4. **无外部查询触发预热**：深夜仅有本测试每 30 分钟触发 16 次查询——不足以维持热度。

## 7. 优化建议

### P1：降低 Compaction 阈值至 15%（长期建议）

- 按当前 1,929/min 增速，25% 需 ~11 小时，15% 需 ~6.5 小时。
- **白天事件风暴时差距会进一步缩小**。

### P2：索引文件 page cache 保持机制

- **问题**：全表扫描路径在无活跃查询时逐步退化（深夜 page cache 被回收）。
- **方案 A**：后台线程每 5 分钟对索引文件做 `madvise(WILLNEED)` 预读——保持 page cache 热度。
- **方案 B**：使用 `mlock()` 锁定索引关键页面——但可能增加内存压力。
- **方案 C**（最轻量）：接受深夜退化，因为白天恢复后自然预热。
- **推荐**：方案 C（不做改动）——495ms 仍在可接受范围，不值得增加系统复杂度。

### P3：无其他优化需求

- 引擎本身运行完美——所有瓶颈均已消除。
- 唯一的变量是 OS 级 page cache 管理——这超出应用控制范围。
