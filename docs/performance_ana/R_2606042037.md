## 6. 问题清单

### Critical：GCD dispatch 延迟——仍为主导瓶颈

- `main.cpp` GCD 开销 14.9 秒（99%），`MacEverything` 3.2 秒（98%），`hello world` 2.6 秒（99%）。
- **查询间存在串行依赖**——前序查询的 I/O 密集操作（如 `.pdf` phase2=3.8 秒）阻塞 GCD 线程池，累积延迟到后续查询。
- **与 R109（全部正常）的区别**：R109 查询时 flush 处于间隙期，本轮查询与 flush I/O 时间窗口重叠。

### High：Flush 仍过于频繁

- 3.3 小时内 161 次 flush——尽管 SKIPFLUSH 增至 11，flush 频率仍偏高。
- 每次 flush rewrite 3-9 秒——期间 GCD 线程可能被 I/O 操作占用。

### 正面：tombstone 稳态良好

- 1.28%（74K 条）——compaction 后 ~3 小时，增速 ~370/min（正常水平）。

## 7. 优化建议

### P0：GCD 查询队列优先级隔离

- **方案**：查询使用高优先级 GCD 队列（`QOS_CLASS_USER_INTERACTIVE`），flush 使用低优先级队列（`QOS_CLASS_UTILITY`）。
- **预期收益**：查询不再被 flush I/O 阻塞。

### P0：降低 flush 频率

- 当前阈值 100 条太低——改为 5,000-10,000 条或增加最小间隔 5 分钟。
- SKIPFLUSH 自然增加说明事件流已减缓——但 flush 仍在不必要地频繁触发。

### P1：查询电池串行执行的 GCD 堆积

- HTTP 服务应使用并发 GCD 队列处理请求——避免单个慢查询阻塞后续请求。

## 8. 下一轮重点

2. GCD 延迟是否在非 flush 窗口恢复正常。

## 9. 结论

**GCD dispatch 延迟仍为主导瓶颈——`main.cpp`=15,071ms（GCD 开销 14,902ms，99%）。** lockWait=0 全部查询，tombstone 仅 1.28%（compaction 后稳态良好）。7/16 >500ms，P50=360ms，Max=15,071ms。flush rewrite 回落至 3-9 秒（R110 的 105 秒膨胀已消退），但 flush 仍在持续运行（161 次/3.3 小时），与查询 I/O 竞争导致 GCD 线程池调度延迟。SKIPFLUSH=11（+7）——事件流密度下降，flush 频率开始自然限流。**性能波动的根因是 flush I/O 与查询 I/O 的竞争**——需要 GCD 队列优先级隔离和降低 flush 频率才能实现稳定性能。
