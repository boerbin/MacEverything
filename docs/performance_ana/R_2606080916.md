## 6. 问题清单

### 观察项：系统睡眠/唤醒冷启动（非 bug）

- **现象**：7/16 >500ms，Max=2217ms，lockWait=32ms。
- **原因**：系统休眠约 1.5h，page cache 完全淘汰，唤醒后全索引冷启动。
- **影响**：唤醒后首批查询延迟——一次性，后续查询自预热恢复。
- **处置**：系统级行为，应用层无法规避。记录备查。

### lockWait=30-32ms（唤醒场景特有）

- **首次突破 10ms 阈值。**
- **原因**：唤醒后 flush timer 和查询线程同时竞争锁。
- **影响**：仅出现在唤醒首批查询，非持续性。
- **COW 方案（P1）可完全消除。**

## 7. 优化建议

### P0：排查 compaction rewrite 崩溃根因（持续建议）

- tombstone 21.38%，距 25% 阈值约 ~21 小时。

### P1：flush rewrite 改为 COW 方式（优先级提升）

- **本轮 lockWait=32ms 首次证明在唤醒场景下 lock 竞争可感知。**
- COW 方案：读路径无锁，写路径 copy-on-write→atomic swap。
- 可完全消除 lockWait，包括唤醒场景。

### P2：唤醒预热策略（可选优化）

- 检测系统唤醒事件（`NSWorkspace.didWakeNotification`），主动触发热点 postings 预读。
- 可将唤醒首查延迟从 2s+ 降至数百 ms。
- 复杂度中等，收益取决于用户唤醒后立即搜索的频率。

## 9. 结论

**系统睡眠/唤醒导致全面冷启动——7/16 >500ms，Max=2217ms，P50=167ms，lockWait=32ms。** 连续 32 轮 0 新增 >500ms 查询的纪录终结——全部 5 个新增 >500ms 查询均为唤醒冷启动导致。冷启动倍率与 candidates 数量强正相关（116K candidates → 202x，14K → 38x，9.8K → 11x）。线性扫描因 readahead 预取仅 3-4x。
