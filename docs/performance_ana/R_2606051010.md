## 6. 问题清单

### High：flush rewrite 70 秒导致查询阻塞 46 秒

- **这是首次发现的严重可用性问题**——用户查询被阻塞近 1 分钟。
- **根因**：flush rewrite 持有写锁期间，所有查询的读锁请求被阻塞。当 rewrite 因磁盘 I/O 竞争耗时异常时，阻塞时间成正比增加。
- **触发条件**：系统级磁盘 I/O 竞争（Time Machine / Spotlight / macOS 维护）。
- **影响**：任何在 flush rewrite 期间发起的查询都会被阻塞至 rewrite 完成。
- **发生频率**：首次观察到——可能是罕见事件（需要 I/O 竞争恰好与 flush 重叠）。

### 架构层面分析

```
当前架构：
  flush rewrite（写锁）→ 阻塞所有查询（读锁）→ rewrite 完成 → 释放

理想架构：
  flush rewrite（后台 COW）→ 不阻塞查询 → 原子切换 → 极短锁窗口
```

- **当前 flush rewrite 将整个索引文件重写（~300MB）——持有写锁全程。**
- **如果 rewrite 被 I/O 竞争拖慢至 70 秒，查询就被阻塞 70 秒。**
- **COW（copy-on-write）方案**：rewrite 写入临时文件 → 完成后原子 rename → 仅在 swap 时持有锁（<1ms）。

## 7. 优化建议

### P0（新增）：flush rewrite 改为 COW 方式——消除长时间锁阻塞

- **当前架构风险**：任何磁盘 I/O 竞争都可能导致 flush rewrite 变慢 → 查询被阻塞数十秒。
- **COW 方案**：
  1. rewrite 写入 `index.tmp` 临时文件（不持有锁）。
  2. 写入完成后，获取写锁 → `rename(index.tmp, index)` → 更新内存指针 → 释放锁。
  3. 锁持有时间从"rewrite 全程"缩短至"rename + 指针更新"（<1ms）。
- **收益**：即使 rewrite 耗时 70 秒，查询也不会被阻塞。
- **风险**：低——rename 是原子操作，crash 安全（旧文件不变）。
- **优先级**：**P0——这是目前唯一可能导致用户感知到"卡死"的问题。**

### P1：降低 Compaction 阈值至 15%（不变）

- 当前 7.45%，白天平均增速 ~1,600/min，约 4.6 小时达到 15%。
- compaction 减少记录数 → rewrite 数据量减小 → rewrite 时间缩短 → 即使无 COW 也减少风险。

### P2：flush rewrite 超时保护

- 如果 rewrite 超过 N 秒（如 10 秒），记录告警日志。
- 考虑在极端情况下 abort rewrite 并使用旧索引继续服务。
- **次于 COW 方案——COW 从根本上消除问题。**

## 9. 结论

**灾难性异常——flush rewrite=70,201ms（70 秒）导致 `x` 查询被阻塞 46,757ms。** 这是本监控系列最严重的单事件故障。根因：flush rewrite 持有写锁全程，当磁盘 I/O 被系统级任务（可能是 Time Machine）占用时，rewrite 从正常 ~2.5 秒暴涨至 70 秒——所有并发查询被阻塞。

**去除异常后系统性能正常**（13 个查询 P50=103ms, Max=257ms），全表扫描 phase2 仍在 52-66ms（接近 R133 极限水平）。**问题完全在 flush 锁架构——不是搜索引擎性能退化。**

**P0 建议：将 flush rewrite 改为 COW 方式**——rewrite 写入临时文件（不持锁）→ 完成后原子 rename（持锁 <1ms）。这从根本上消除了 I/O 竞争导致查询阻塞的风险。tombstone 7.45%（464K），15% compaction 预计 ~14:50。
