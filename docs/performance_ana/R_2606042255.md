## 6. 问题清单

### High：Flush 频率回弹——从 3.2 次/小时暴涨至 77 次/小时

- **R112 观测到的 3.7 次/小时是假象**——仅维持了极短时间。
- **原因**：tombstone 增速从 R112 的 ~260/min 加速至 ~1,560/min（文件系统活动突然增加），触发频繁 flush。
- **直接后果**：flush rewrite 峰值 27 秒，GCD 线程池再次被 I/O 占用。

### High：GCD dispatch 延迟回升

- `test` GCD=1,095ms，`MacEverything` GCD=1,004ms，`main.cpp` GCD=775ms，`README` GCD=653ms。
- 与 R112（max GCD=1,052ms）持平——但影响查询数从 3 个增至 4 个。
- **原因**：flush rewrite 27 秒峰值期间 GCD 线程池被 I/O 操作阻塞。

### High：Phase2 I/O 退化

- `content:import` phase2 从 272ms(R112) 退化至 1,934ms——**7 倍退化**。
- `path:/Users` phase2=1,220ms（R112=732ms——1.7 倍退化）。
- **原因**：flush 高频 I/O 导致磁盘读取队列拥塞，查询的随机读取被严重延迟。

### Medium：Tombstone 增速加快

- R112→R113：+7,845 条/5 分钟 = ~1,560/min。
- R111→R112：~260/min。
- **增速跳升 6 倍**——文件系统有突发活动（可能是 IDE 操作、Time Machine、Spotlight 等）。
- tombstone 1.65% 仍远低于 25% compaction 阈值——暂无风险。

### 正面：lockWait 基本消除

- 仅 `dm:today` lockWait=6.3ms——可忽略。
- **锁竞争已不是瓶颈**——验证 R109 之后的锁优化效果持久。

## 7. 优化建议

### P0：Flush 频率动态限流

- 当前固定阈值（100 条 pending changes）导致 flush 频率随事件流密度剧烈波动。
- **方案**：引入最小间隔限制（如 2-5 分钟），即使超过 100 条 pending 也等待间隔到期。
- **预期收益**：避免 flush 频率从 3/hr 突变到 77/hr。

### P0：GCD 队列优先级隔离

- flush rewrite（最大 27 秒）仍在阻塞查询 GCD 调度。
- **方案**：查询使用 `QOS_CLASS_USER_INTERACTIVE`，flush 使用 `QOS_CLASS_UTILITY`。
- **预期收益**：查询不受 flush I/O 影响。

### P1：Phase2 I/O 优先级

- pure-filter 和 linear-gcd 路径的 phase2 读取被 flush 写入阻塞。
- **方案**：查询 I/O 使用 `F_RDADVISE` 预读或高优先级 I/O 通道。

### P2：Tombstone 增速监控与自适应 flush

- 当 tombstone 增速突然跳升时，应降低 flush 频率而非加速——避免 I/O 风暴。
- **方案**：当检测到 flush rewrite >15 秒时，自动将最小间隔延长至 5 分钟。

## 9. 结论

**Flush 频率突增回弹——从 R112 的 3.2 次/小时暴涨至 ~77 次/小时（24 倍），导致性能退化。** P50=285ms（R112=157ms，↑1.8 倍），Max=1,943ms（R112=1,071ms，↑1.8 倍），7/16 >500ms（R112=5/16）。GCD dispatch 延迟仍为主导瓶颈之一（`test` 1,095ms、`MacEverything` 1,004ms），同时 phase2 I/O 退化显著（`content:import` 1,934ms，R112 的 7 倍）。flush rewrite 出现 27 秒峰值（R112 仅 4-9 秒）。tombstone 1.65%（正常增长），lockWait 基本消除（6.3ms）。**R112 观测到的 flush 低频状态是短暂间隙——系统事件流在 ~5 分钟后再次密集化，flush 频率随之暴涨。**真正的稳态需要 flush 最小间隔限制（不依赖事件流密度）+ GCD 队列优先级隔离。
