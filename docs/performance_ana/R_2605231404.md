## 3. 问题诊断

### 3.1 【严重】墓碑（tombstone）堆积，27h 内 1 in 5 记录已死 — 但 COW compaction 从未触发

- **现象**：`liveRecords` 仅增长 67k，但 `total` 多了 1.09M。墓碑占比由 6.2% 攀升到 20.6%，且单调递增。
- **量化**：所有走 linear-gcd / linear-scan 的查询都会多扫 ~20% 的死记录，相当于把热路径搜索性能拖慢 1.25×。
- **根因怀疑**：
  1. 日志中存在 `Auto-compaction started (initial interval 300s)`，但全程 **没有一条 compaction 完成日志**——压根没跑过 COW compaction。
  2. 即便跑了，依据之前 [[change S3962]] / S3968 的记忆，COW compaction 不会重建 `ShortQueryCache`、`ContentIndex` 的 index remap。
  3. 触发阈值可能设置得过高（仅按时间触发？按墓碑比例触发？需要查 `IndexPersistence::compactRecords` 触发条件）。
- **影响**：长跑情况下，索引体积线性膨胀，`.h` 等 linear-gcd 查询时延上不封顶。

### 3.2 【严重】Flush 风暴：实际间隔 49s，是配置值的 1/6

- **现象**：86% 的 flush 紧跟前一次（<60s 间隔）。30s/30s/30s 这种节奏在会话末尾持续出现。
- **量化**：每次 flush 把 6.6M 记录序列化写盘（即便采用 paged/COW），**单日 2k+ 次** = 数十 GB 写放大，SSD 写寿命与 IO 带宽被严重占用。
- **根因怀疑**：写门限触发器（如「累计 N 条变更则触发」）阈值过低，被高频 FSEvents（5M+ 文件被 watch `/`）频繁打满；时间触发与事件触发未做 debounce 协同。
- **二级影响**：与查询线程在 `IndexLock` 上抢锁，解释了 §1.3 中 HTTP `.h` 时延翻倍的现象。

### 3.3 【严重】"Failed to flush paged index" ERROR 反复出现，根因日志缺失

```
[18:20:13] [ERROR] [IndexPersistence] Failed to flush paged index — keeping old WAL for recovery
[18:22:26] [ERROR] [IndexPersistence] Failed to flush paged index — keeping old WAL for recovery
[05:38:00] [ERROR] [IndexPersistence] Failed to flush paged index — keeping old WAL for recovery
[05:38:03] [ERROR] [IndexPersistence] Failed to flush paged index — keeping old WAL for recovery
[11:39:31] [ERROR] [IndexPersistence] Failed to flush paged index — keeping old WAL for recovery
```

- **现象**：5 次 ERROR，每次紧跟一次成功的 v6 flat flush，下一次 paged flush 又恢复。
- **症状**：**根因不明**——ERROR 日志没有 errno / 异常 message / 失败阶段，仅一句兜底。下次发生时还是无法定位。
- **风险**：如果 paged index 是 ShortQueryCache 等增量结构的承载，长期失败会导致 cache 永远停留在旧版本（[[change S3970]] 中刚修过类似 stale-cache 问题）。
- **优先级**：必须先**补充错误现场**（写入 errno、文件 fd、剩余空间、调用栈），再谈修复。

### 3.4 【严重】查询解析对括号不友好：`xxx (1)` 类文件不可搜

```
q=(test)     results=0
q=test(1)    results=0
q=test (1)   results=0   ← 候选 126,799 → 实际 0
q=(1)        results=5
```

- **现象**：含 `()` 的字面量查询被解析器吞掉。`test (1)` 的 trigram 拿到 12.6w 候选，但二阶过滤把全部判负——说明把括号当成了某种语法（分组 / 通配 / NOT）。
- **影响**：macOS 自动重命名生成的 `xxxx (1).png` 大量存在；某些库目录如 `Resources (en)` 完全搜不到。
- **根因怀疑**：`QueryParser::tokenize` 把 `(`/`)` 当 grouping operator；未在「字面量模式」下转义。

### 3.5 【中】扩展名查询永远走 linear-gcd 慢路径

- **现象**：`.h` 在 26 次内部 bench 中全部记录 `path=advanced-linear-gcd candidates=0`，时延 200~472ms；其他点开头的查询同样如此（除非长度 ≥4 让 trigram 命中）。
- **根因**：trigram 索引以 3-gram 为最小单元，`.h` 仅 2 字符（`.`+`h`）无法构造 trigram，回退到 linear 扫描全部 6.6M 记录。
- **影响**：扩展名是最常见用户查询之一，热路径不应走 O(N)。

### 3.6 【中】AI 翻译上下文窗口拥挤 + 翻译质量偏弱

- **现象**：`LlamaBackend chat: nTokens=1392 n_ctx=2048 n_batch=2048` —— prompt + 59 few-shot 已占 **68% 上下文**。
- **症状**：
  - 留给生成的 token ≤ 656，长查询易截断；
  - 翻译质量：`图片` → `pic:`（残缺）、`项目中所有的cpp文件` → `content:cpp`（应为 `ext:cpp`，且 content 检索是空的）。
- **量化**：infer 中位数 342ms 已合理，但 HTTP 端到端 800~1600ms，HTTP 侧 ~500ms 是 JSON+网络+加锁开销。

### 3.7 【低】Short-query-cache 在重复采样下出现 ms→s 的抖动

- 单跑 `a`=189ms，连跑 `a`=1369ms。
- 与 §3.2 flush 风暴时间窗强相关：每 30s 一次 flush 时，cache 重建/校验 vs 查询读取在同一把锁上排队。
- 建议：（1）查询路径用 `shared_lock`；（2）flush 写入用临时文件 + rename，避开读路径。

### 3.8 【低】HttpServer 完全没有访问日志

- 日志里只有启动那一句 `Listening on 127.0.0.1:19860`。
- 全程没有 request/response 计时，给生产排错增加困难。
- 与内部 `SearchEngine::QueryAdvanced` 一致格式打一行即可。

## 6. 一句话结论

> 当前实例**功能可用但内部健康度持续恶化**：墓碑占比 20%、flush 频率超配置 6×、5 次匿名 ERROR、`(1)` 类文件搜不到、扩展名查询走 O(N)。建议立即上线 P0 四项（flush 限流 / 错误现场 / 括号修复 / compaction 触发），其余按 P1/P2 滚动。
