## 9. 可能问题定位

### P0-1：24% tombstone ratio 下 reclaim 仍不触发，扫描与 rewrite 压力持续累积

证据：

- `tombstoneRatio=24.23%`，距离 25% 只剩约 `0.77pp`。
- `COMPACTION=2 / RECLAIM=0`。
- 相对上一轮，tombstones 增加 `31,473`，live records 只增加 `2,708`。

根因判断：25% runtime reclaim valve 对当前负载过迟。系统在 23–24% 区间已经出现 content/中文慢查询与 full-scan floor 升高，但回收仍未介入。

### P0-2：rewrite cluster 让 full-scan page residency 持续处于冷/半冷状态

证据：

- 本轮新增 18 次 ≥5s rewrite，`FLUSH_GE5` 从 166 升至 184。
- `content/path/中文` floor 分别为 `204.67 / 173.32 / 206.33ms`，较上一轮继续升高。
- Trigram/ext-index 热路径正常，说明问题主要集中在 full-scan 访问页，而不是所有索引都退化。

根因判断：连续 rewrite 对 mmap/page-cache 的扰动没有被 prewarm 或节流吸收，导致 full-scan 所需页面长期不稳定。

### P0-3：full-scan 仍在锁内执行，平台性退化会转化为锁持有

证据：

- `content:import total=169.88ms / lockHeld=160.49ms`。
- `path:/Users total=223.70ms / lockHeld=211.39ms`。
- `中文测试 total=201.93ms / lockHeld=201.90ms`。

根因判断：当前 170–220ms 的平台性退化会直接扩大锁持有时间；当同类路径再次出现 500ms+ 尾部时，也会等比例放大全局阻塞风险。

### P1：trigram 冷尖峰缓解，但高频候选 query 仍有波动

证据：

- `.pdf` battery 已从上一轮 `217.98ms` 降到 `12.16ms`。
- `test` reprobe 有 `35.07ms`、`38.09ms`，但低于 full-scan 风险。

根因判断：trigram 索引页相对容易热化；当前优先级仍应放在 full-scan/page residency 和 storage debt。

## 10. 优化建议

### P0：立即降低 runtime reclaim threshold 或引入 debt-based reclaim

- 当前 `24.23%` 已接近 25%，但问题从 22–23% 就开始出现。
- 建议把阀值降到 8–10%，或按 `tombstone ratio + absolute tombstones + rewrite density + slow-query signal` 触发 reclaim。
- 验收标准：`RECLAIM>0`，tombstone ratio 回落到 10% 以下，`FLUSH_GE5` 增速下降，full-scan floor 不再随 tombstones 上升。

### P0：增加 rewrite density guard

- 当短窗口内出现多个 ≥5s rewrite，尤其连续 ≥10s rewrite 时，合并、推迟或降频后续 rewrite。
- 本轮 14:14–14:42 新增 18 次 ≥5s rewrite，是 full-scan floor 全面升高的直接背景。
- 验收标准：连续 rewrite cluster 后，`content/path/中文` reprobe floor 不再保持 170–200ms 级。

### P0：targeted prewarm content/path/中文相关页面

- rewrite 完成后预热 content/path/中文匹配会访问的字符串页和路径页，或使用 `madvise(WILLNEED)` 提示关键 mmap 区域。
- 不建议全量常驻内存；目标是降低 rewrite 后第一批 full-scan query 的冷页成本。
- 验收标准：`content/path/中文` W1/W2/reprobe floor 回到 40–60ms 区间，不再维持 170–200ms 平台。

### P0：读写解耦，避免锁内 page fault

- 查询使用不可变 snapshot；flush/rewrite 通过 pointer swap 发布新版本。
- 优先处理 `advanced-linear-gcd` 与 `advanced-pure-filter-soa-gcd`，它们的 `lockHeld≈phase2≈total` 最明显。
- 验收标准：即使 full-scan 业务耗时升高，`lockHeldMs / totalMs` 也不再接近 1。

### P1：增加 reclaim 前后对比实验

- 当 tombstone ratio 接近或超过 25% 后，观察是否出现 `RECLAIM>0`，并记录 reclaim 前后的 `recordCount/liveRecordCount/tombstones/full-scan floor/rewrite duration`。
- 如果 25% 后仍无 reclaim，说明阀门逻辑可能不是简单 ratio 或存在运行条件约束。
- 验收标准：明确 reclaim valve 的真实触发条件，并验证回收是否降低 full-scan floor。

## 11. 结论

本轮没有新增 ≥500ms 慢查询，但性能风险继续升高：`tombstoneRatio=24.23%`、`FLUSH_GE5=184`、`FLUSH_GE10=27`、`RECLAIM=0`，且 `content/path/中文` 的 reprobe floor 全部维持在 `173–206ms`。这说明上一轮中文 1s 慢查询 cluster 之后，系统没有恢复到健康热态，而是停留在高平台退化状态。下一步最重要的是验证 25% reclaim valve 是否会触发；但从优化角度看，不应等待 25%，应尽快实施 debt-based reclaim、rewrite density guard、targeted prewarm 和读写解耦。
