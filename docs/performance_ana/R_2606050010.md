### lockWait 回归分析

- R109-R114：lockWait=0（全部查询，6 轮连续）。
- R115：lockWait max=18.6ms（可忽略）。
- **R116：lockWait max=762.8ms（3/16 查询受影响）。**
- **原因**：tombstone 增速 ~22,000/min——每秒 ~370 个 FSWatcher 事件写入 WAL——写入持锁时间增加，查询等锁时间激增。
- **对比 R106**：R106 tombstone=18.88%，lockWait=304ms。本轮 tombstone=17.92%，lockWait=762ms——**同等 tombstone 比例下 lockWait 更严重**——说明事件流密度比 R106 时更高。

### `abc def ghi jkl mno pqr`=5,975ms 极端延迟

- phase2=1,221ms + GCD 开销=4,754ms。
- **GCD 99% 由调度延迟贡献**——查询在队列中等待 ~4.8 秒。
- **原因**：该查询排在 `size:>100m`(phase2=2,263ms) 之后——前序查询的 I/O 密集操作阻塞了 GCD 线程池。
- **串行执行效应**：前 7 个查询的累积延迟直接影响第 8 个查询的调度时间。

### `size:>100m` phase2=2,263ms 异常

- R115: `size:>100m` phase2=26ms（page cache 热）。
- **R116: phase2=2,263ms——87 倍退化。**
- **原因**：page cache 被大量 flush I/O 和 FSWatcher 事件活动挤出——pure-filter 路径重新变为磁盘随机读取。

## 6. 问题清单

### Critical：事件风暴导致全面退化

- tombstone 增速 ~24,000/min——系统正经历大规模文件系统变更。
- **三重瓶颈同时激活**：lockWait(762ms) + GCD 延迟(4,754ms) + phase2 I/O(2,263ms)。
- **page cache 被挤出**——R115 的 60ms 全表扫描不再可能。
- **这是 R106-R108 退化周期的重现**——需要等待 compaction 恢复。

### High：lockWait 回归——WAL 写入锁竞争

- 3/16 查询受影响（max 762ms）——每秒 ~400 个事件写入 WAL。
- **与 R104-R106 的模式一致**——高事件流密度→WAL 写入持锁→查询等锁。
- **compaction 将通过重置 tombstone 和减少事件流来间接解决**。

### High：Flush 文件膨胀

- recordCount 从 5.84M(R114) 增至 7.0M(R116)——文件中多了 1.17M 行 tombstone 记录。
- **flush rewrite 时间与文件大小正相关**——7.0M 记录的 rewrite 耗时 42 秒。
- **compaction 将文件缩小回 ~5.75M（仅保留 live records）**——rewrite 时间将回落至 1-3 秒。

### 正面：系统自愈机制即将生效

- 25% compaction 阈值 = ~1.92M tombstone（当前 1.25M）。
- **按当前增速 ~28 分钟内触发——系统将自动恢复。**
- COW compaction 机制经 R108-R109 验证有效。

## 7. 优化建议

### P0：降低 Compaction 阈值（长期优化）

- 当前 25% 太高——系统在 17-25% 区间经历严重退化。
- **方案**：降至 10-15%——更早 compaction，退化窗口从 ~2 小时缩短至 ~30 分钟。
- **权衡**：compaction 更频繁，但每次更快（tombstone 更少→compaction 数据量更小）。

### P0：WAL 写入锁粒度优化

- lockWait 762ms 说明查询等待 WAL 写入释放锁。
- **方案**：批量 WAL 写入（每 100ms 或 1000 条事件批量持锁一次），而非每条事件独立持锁。
- **预期收益**：lockWait 降至 <10ms。

### P1：Index 文件膨胀控制

- 7.0M 记录（含 1.25M tombstone）→flush rewrite 42 秒。
- **方案**：flush 时主动跳过 tombstone 行（写入时过滤）——等效于"每次 flush 自带 mini-compaction"。
- **预期收益**：flush rewrite 时间稳定在 1-5 秒，不随 tombstone 增长。

### P1：Page cache 保护

- 高频 flush + 事件 I/O 挤出了查询所需的 page cache。
- **方案**：查询使用 `mmap` + `madvise(MADV_WILLNEED)` 锁定索引文件核心页面。

## 9. 结论

**严重退化——10/16 >500ms，P50=909ms（R115=27ms，↑34 倍），Max=5,975ms。lockWait 回归 762ms（3/16 查询）。** tombstone 飙升至 17.92%（1,254K），增速 ~24,000/min——系统正经历大规模文件系统事件风暴。三重瓶颈同时激活：lockWait(WAL 锁竞争) + GCD 延迟(flush I/O 占用线程池) + phase2 I/O(page cache 被挤出)。flush rewrite 峰值 42 秒（index 文件膨胀至 7.0M 记录）。**R115 的历史最佳仅维持 30 分钟——tombstone 事件风暴摧毁了 page cache 优势并重新激活锁竞争。**

**系统正在重复 R106→R108→R109 的退化-恢复周期。** 按当前增速，~28 分钟后触发 COW compaction（25% 阈值），之后性能将再次恢复。**根本解决方案**：降低 compaction 阈值至 10-15%（缩短退化窗口）、WAL 批量写入（消除 lockWait）、flush 时过滤 tombstone（控制文件膨胀）。
