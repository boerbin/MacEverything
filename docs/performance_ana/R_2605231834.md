## 3. 问题诊断

### 3.1 【P0】墓碑占比 23%，compaction 32h 从未完成

live 仅增 76k，tombstone 膨胀到 1.59M。`Auto-compaction started (initial interval 300s)` 但全程无 compaction 完成日志。线性扫描（`.h` 走 advanced-linear-gcd）多扫 23% 死记录。触发阈值可能仅按时间，被高频 flush 永远打断。

### 3.2 【P0】Flush 风暴：89% <60s，配置 300s 形同虚设

2,541 次 flush / 32h ≈ 每 45s 一次。每次序列化写 ~6.8M 记录，日写放大数十 GB。FSEvents 事件触发阈值远低于时间触发，两者未 coalesce。

**二级影响**：flush 与查询在 `IndexLock` 上互斥 → HTTP 端 1.6~3.4s 抖动（内部计时 200~472ms，差值即锁等待）。

### 3.3 【P0】"Failed to flush paged index" ERROR ×7，根因现场全缺

7 次分 4 个时间簇（18:20/18:22、05:38/05:38、11:39、17:37/17:37）。错误无 errno/path/freeBytes/stage。paged index 失败 → ShortQueryCache 可能停留在旧版本。

### 3.4 【P1】扩展名查询 HTTP 端到端 1.6~3.4s

`.h` 内部计时 354~472ms，HTTP 端 1.8~3.3s。扩展名是最常见查询之一，热路径走 linear-gcd O(N)。

### 3.5 【P1】AI 翻译质量

prompt 占 68% 上下文（1392/2048 tokens）。`图片→pic:` 残缺（pic: 非合法 filter），`项目中所有cpp→content:cpp` 但 `contentIndexedFileCount=0`。

### 3.6 【P1】括号解析 bug

`(` / `)` 被 QueryParser 当语法 token，未作字面量 escape。`test (1)` 类文件全不可搜。

### 3.7 【P2】Content 索引未构建

`contentIndexedFileCount=0`，内容搜索全量不可用。

## 4. 优化建议

| 优先级 | 行动项 | 预期收益 | 成本 |
|---|---|---|---|
| **P0** | flush 限流（min_interval=300s 硬下限 + token-bucket） | 写盘降 5×，锁竞争消除 | S |
| **P0** | ERROR 补全（errno/path/freeBytes/stage） | 让 #3.3 可定位 | XS |
| **P0** | compaction 按墓碑比例 ≥15% 触发 | 线性查询提速 1.25× | S |
| **P0** | QueryParser 括号当字面量 | 修一类文件搜不到 | S |
| P1 | 扩展名倒排索引 | `.h` 类 300ms→<10ms | M |
| P1 | HTTP 访问日志（每请求一行） | 可观测性 | S |
| P1 | shared_lock 分离 search/flush | 时延抖动归零 | M |
| P1 | AI prompt 精简至 20 few-shot | infer p95 降 ~30% | S |
| P2 | paged-index 增量 flush（diff-based） | SSD 友好 | L |
| P2 | Content 索引首次构建 | 内容搜索可用 | M |

## 5. 一句话结论

> **功能可用但健康度恶化**：tombstone 23%、flush 45s 平均、7 次匿名 ERROR、`test (1)` 全不可搜、扩展名 HTTP 端 1~3.5s。立即上线 P0 四项（flush 限流 / ERROR 现场 / compaction 触发 / 括号修复）。
