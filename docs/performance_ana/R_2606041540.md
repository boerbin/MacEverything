## 6. 问题清单

### Critical：tombstone 灾难——29.30%（2,382,609 条，714MB）

- **单轮 +1,582,964 条——R100 的 6.8 倍，历史最高的 60 倍。**
- **从 12.21% 直接跳至 29.30%**——tombstone 占总记录近三分之一。
- **714MB 额外内存占用**——是系统正常运行时总内存的重大负担。
  - R95 (8%, 150MB) → 开始出现 I/O 压力游走
  - R99 (9%, 170MB) → 全路径 I/O 饱和
  - R100 (12%, 240MB) → lockWait 广泛爆发
  - **R101 (29%, 714MB) → 系统在异常状态运行**
- **linear 扫描成本**：recordCount 8.13M 中 2.38M 是 tombstone——linear 查询扫描了 29% 的无效记录。
- 连续第 41 轮超 2%，首轮超过 29%。

### Critical：I/O 压力基线持续恶化（第 3 轮）

- `.pdf`=766ms，`path:/Users`=627ms。
- R99（Max=8,495ms）→ R100（Max=2,887ms）→ **R101（Max=766ms）**——峰值在下降但 >500ms 查询持续存在。
- **714MB tombstone 下查询延迟"仅"766ms 的原因**：连续 3 轮查询电池预热了部分页面缓存。一旦系统空闲一段时间（缓存冷却），下次查询将面临更严重的页面故障。
- **风险**：当前 29.30% 下的"正常"性能是脆弱的——任何额外 I/O 活动（编译、文件浏览等）都可能触发比 R86 更严重的灾难。

### Critical：lockWait 常态化（14/16 查询受影响）

- 连续第 2 轮 >13/16 查询有锁等待。
- 最高 15.3ms（R100=19.7ms，略降）。
- **零候选集查询也有 14.5ms lockWait**——锁竞争完全由 FSWatcher 事件写入驱动，与查询本身无关。

### Critical：SKIPFLUSH +56 确认事件风暴持续

- R100→R101 间隔内 FSWatcher 事件量是正常水平的 4.7 倍。
- 事件源（大规模系统活动）**尚未停止**——如果持续，下一轮 tombstone 可能突破 40%。

### Critical：FLUSH=0 + tombstone 29.30% 机制灾难

- 2.38M 条 tombstone 中没有任何一条被 flush/compaction 清理。
- WAL flush 阈值在高频事件流下完全失效——这是 tombstone 从 2% 增长到 29% 的根本原因。
