## 6. 问题清单

### P0：tombstone 已突破 14%

- 证据：tombstone=877,465（14.18%），较上一轮增加 15,508。
- 影响：无效记录比例继续升高，会放大扫描成本、索引重写成本与 compaction 压力。
- 判断：这是本轮最重要的新风险信号，说明 compaction/清理策略仍未追上更新与删除积累速度。

### P0：scan/filter 尾部仍高位

- 证据：`中文测试`=366.3ms，`content:import`=207.7ms，`path:/Users`=207.0ms，`dm:today`=82.2ms；scan/filter 路径总和约 904.2ms。
- 影响：虽然未超过 500ms，但多个扫描/过滤查询仍处于用户可感知区间。
- 判断：主要耗时在 phase2，lockWait=0ms，根因仍偏向扫描量、tombstone、page-cache 状态或缺少剪枝。

### P0：新 session 仍有秒级完整 flush，且没有退避

- 证据：新 session `FLUSH=2`，`SKIPFLUSH=0`，flush total 分别为 4812ms 与 3437ms。
- 影响：完整重写仍会制造 I/O 与 page-cache 干扰，可能解释 trigram 与 scan/filter 查询在不同轮次间波动。
- 判断：session 重启只清空了旧日志上下文，没有改变 flush 结构性风险。

### P1：trigram 路径也出现中高位波动

- 证据：`hello world`=210.4ms，`*.swift`=93.6ms，`abc def ghi jkl mno pqr`=89.9ms，`.pdf`=48.6ms。
- 影响：trigram 虽未超标，但已经不再全部落在极佳区间；在 flush/page-cache 冷却后仍可能重新出现 >500ms 尾部。

### P1：中文查询仍依赖 linear-gcd

## 7. 优化建议

### P0：立即提前或分段 compaction

- 以 tombstone 率 14% 作为明确触发信号，不再等待更高阈值。
- 结合绝对 tombstone 数、segment tombstone 率和 flush rewrite 成本触发局部 compaction。
- 优先处理 tombstone 密集 segment，避免 scan/filter 路径继续扫描大量无效记录。
- 验收：tombstone 率从 14.18% 回落，`中文测试`、`content:import`、`path:/Users` 稳定 <200ms。

### P0：flush 改为增量/COW 页写入

- 将 stable segment 与 delta segment 分离，常规 flush 只追加或替换小段 delta。
- 大段合并放到后台低优先级任务，不与前台查询争抢热页或持锁窗口。
- 验收：常规 flush total <200ms，新 session 不再出现 3-5s 级完整 rewrite。

### P0：增加 flush I/O 压力退避和前台保护

- 当最近 flush 超过阈值时，提高下一次 flush 间隔、降低 batch 频率，或前台查询活跃时推迟大 flush。
- 持久化线程使用低 QoS，并评估大顺序写的 `F_NOCACHE`/同类策略，减少对搜索热页的冲刷。
- 验收：`SKIPFLUSH` 不再长期为 0，query battery 不再在 flush 后出现 200ms+ trigram 或 300ms+ linear-gcd。

### P0：为 advanced-linear-gcd 与 pure-filter 增加轻量剪枝

- 对中文、路径、content/filter 类查询记录扫描记录数、tombstone 跳过数和 segment 分布。
- 评估轻量字符 n-gram、路径分段索引、预过滤位图或 segment-level skip list，以减少无结果或低选择性查询的全量扫描。
- 要求保持内存增长可控，优先使用压缩或按需结构，不引入大常驻索引。
- 验收：`中文测试` 不再成为稳定 Max，`content:import` 和 `path:/Users` 稳定低于 200ms。

### P1：细分 trigram/postings 路径

- 对 `advanced-trigram` 记录 postings 读取、候选交并、候选评分、路径加载、结果组装、page-cache miss 近似指标。
- 重点解释 `hello world`=210.4ms 与 `*.swift`=93.6ms 是 postings 读取、候选处理、结果加载还是 page-cache 问题。
- 验收：trigram 查询在 flush 后仍稳定 <100ms，或至少能解释每个阶段的成本。

### P1：拆分 top-level query timing

- 对所有路径增加 queueWait、phase2、candidate materialization、path/file metadata load、sort/rank、result assembly、HTTP serialization/write 等阶段耗时。
- 验收：`queryTimeMs - phase2Ms - lockWaitMs` 不再是不可解释的大黑盒。
