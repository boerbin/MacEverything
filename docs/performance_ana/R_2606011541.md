## 7. 问题清单

### High：tombstone ratio 已达 24.67%，但 `RECLAIM=0`

- 证据：`FINALSTATUS|7296206|5495933|1800273|24.67`，日志 `RECLAIM=0`。
- 影响：full-scan 路径继续扫描 7.29M 总槽位，其中约 1.80M 是 tombstone。无效扫描面已经接近四分之一。
- 根因判断：reclaim 触发阈值或触发条件仍晚于查询性能退化发生点。
- 风险：如果越过 25% 后仍不 reclaim，则说明阀门条件与实际运行状态不一致；如果越过后突然大规模 reclaim，也可能引入新的 flush/rewrite 长尾。

### High：`path:/Users` 线性路径仍可稳定触发 ≥500ms

- 证据：日志新增 `path:/Users=527ms/510ms`，probe 中也出现 527.50ms 和 510.51ms。
- 影响：path 搜索是用户高频交互路径，500ms 级延迟会直接表现为搜索卡顿。
- 根因判断：path 线性扫描仍依赖大范围字符串列访问，受 tombstone 扫描面和页面驻留影响。

### Medium：full-scan 工作仍在锁内完成

- 证据：`path:/Users` battery `phase2Ms=209.73`、`lockHeldMs=209.73`；`中文测试` battery `phase2Ms=186.30`、`lockHeldMs=186.81`；`content:import` battery `phase2Ms=169.85`、`lockHeldMs=169.86`。
- 影响：即使单次查询只有 180–220ms，也会持有锁接近同等时长，容易在并发下放大尾延迟。
- 根因判断：查询执行与共享索引访问的锁粒度仍过粗。

### Medium：flush 长尾继续增长

- 证据：`FLUSH_GE5` 从 200 增至 216，`FLUSH_GE10` 从 33 增至 37。
- 影响：持续长 flush 可能扰动 page cache，并在后续轮次再次触发 content/path/中文秒级慢点。
- 根因判断：flush/rewrite 仍缺少对查询热路径的隔离与限速。

### Low：trigram 冷首轮仍有中等延迟

- 证据：`README` battery 147.00ms，但 reprobe 2ms 级；`abc def ghi jkl mno pqr` battery 161.45ms，reprobe 3ms 级。
- 影响：首轮体验有波动，但相比 full-scan 风险较低。
- 根因判断：候选页或 trigram posting 首次访问存在冷态成本。

## 8. 优化建议

### P0：立即验证 25% reclaim 阀门

当前 24.67% 已非常接近阈值。下一轮应重点验证：

1. tombstone ratio 是否越过 25%；
2. 越过后 `RECLAIM` 是否从 0 增加；
3. reclaim 是否伴随更多 `FLUSH_GE10` 或查询慢点。

如果 ratio >25% 且 `RECLAIM=0`，应优先审查 reclaim 触发条件，而不是继续优化查询微路径。

### P0：将 reclaim 策略前移或改为 debt-based

上一轮 24.48% 已出现多路径秒级慢查询，本轮 24.67% 虽回暖但债务更高。建议不要等到 25% 才尝试回收：

- 将 runtime reclaim 目标阈值前移到 8–10%；
- 或引入 debt-based 策略，结合 tombstone 数量、full-scan 延迟、flush 长尾动态触发；
- reclaim 必须分批限速，避免一次大 rewrite 造成新的页面扰动。

### P1：优先治理 `path:/Users` 线性扫描

本轮唯一新增慢查询都来自 path 路径。建议：

- 给 path 查询增加更强的前置剪枝或索引；
- 对 path lower pool / path string pages 做 targeted prewarm；
- 增加 per-chunk latency 统计，定位是否少数 chunk 拖慢整体；
- 如果可行，将 path 查询从全槽扫描改为更窄的路径 token/segment 索引。

### P1：缩短 full-scan 锁持有时间

建议评估 immutable snapshot 或 pointer-swap publication，让查询在线性扫描时尽量不持有全局共享锁。至少应把 phase2 内部读锁范围缩小到必要元数据获取，而不是覆盖整个扫描过程。

### P2：补齐 full-scan 内部观测

建议在 `advanced-linear-gcd` 和 `advanced-pure-filter-soa-gcd` 记录：

- scanned slots / skipped tombstones；
- chunk p50/p95/max；
- path/content/string/metadata 分段耗时；
- 是否发生明显 page fault 或冷页访问。

这些指标能将当前“page residency 影响”的推断变成可定位的证据。

## 9. 下一轮重点

1. 继续运行相同 query battery，保持可比性。
2. 重点记录 tombstone ratio 是否越过 25%。
3. 重点检查 `RECLAIM` 是否仍为 0。
4. 若出现 reclaim，观察 `FLUSH_GE5/GE10` 和慢查询是否同步增加。
5. 继续把 `path:/Users` 作为本阶段第一敏感探针。

## 10. 结论

本轮读路径从上一轮的多路径秒级慢查询簇中明显回暖，新增 ≥500ms 慢查询只有两条，且都属于 `path:/Users`。但这不能解释为问题消失：tombstone ratio 已升至 24.67%，`RECLAIM=0`，flush 长尾继续增加，full-scan 查询仍在锁内执行。

当前系统最大的风险是 reclaim 阀门即将被触达，但它是否能正确、平滑地工作仍未验证。短期优化优先级应是验证并前移 reclaim，其次才是对 path/content/中文 full-scan 路径做更细的索引与锁粒度优化。
