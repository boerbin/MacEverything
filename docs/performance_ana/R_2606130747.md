## 7. 优化建议

### P0：立即提前或分段 compaction

- 不等待更高的全局 tombstone 阈值；结合绝对 tombstone 数、segment tombstone 率和 flush rewrite 成本触发局部 compaction。
- 优先处理 tombstone 密集 segment，避免 scan/filter 路径继续扫描大量无效记录。
- 验收：tombstone 率从 12%+ 回落，`中文测试`、`content:import` 与 `path:/Users` 稳定 <300ms。

### P0：flush 改为增量/COW 页写入

- 将 stable segment 与 delta segment 分离，常规 flush 只追加或替换小段 delta。
- 大段合并放到后台低优先级任务，不与前台查询争抢热页或持锁窗口。
- 验收：常规 flush total <200ms，latest session 不再出现分钟级 rewrite outlier，lockWait 不再出现 50ms+。

### P0：增加 flush I/O 压力退避和前台保护

- 当最近 flush 超过阈值时，提高下一次 flush 间隔或降低 batch 频率。
- 前台查询活跃或 I/O 延迟升高时推迟大 flush。
- 持久化线程使用低 QoS，避免冲掉搜索路径 page cache。

### P1：为 scan/filter 路径增加剪枝

- 对中文、路径、content/filter 类查询记录扫描记录数和跳过原因，评估轻量字符 n-gram、路径分段、预过滤位图或 segment-level skip list。
- 要求保持内存增长可控，优先使用按需或压缩结构，而不是常驻大索引。
- 验收：`content:import`、`path:/Users`、`中文测试` 稳定低于 300ms，并能解释每次扫描规模。

### P1：补充 lockWait 与后台状态关联观测

- 记录每次查询锁等待对应的 flush/update 状态、持锁线程、等待阶段和持锁耗时。
- 验收：解释上一轮 `content:import` 67.6ms lockWait 是 flush、索引更新还是其他写路径导致。

### P1：拆分扫描路径和 trigram 路径耗时

- 对扫描路径记录扫描记录数、tombstone 跳过数、过滤耗时、排序耗时和结果组装耗时。
- 对 trigram 路径记录 postings 读取、候选集交并、排序、路径加载和结果组装耗时。
- 验收：能解释 scan/filter 100-300ms 与 trigram 偶发差值。

### P2：保护搜索热数据 page cache

- 对 flush 大顺序写考虑 `F_NOCACHE` 或同类策略。
- 对 full-scan/SoA/postings 热区使用预热或访问提示，减少 flush 后冷启动波动。
