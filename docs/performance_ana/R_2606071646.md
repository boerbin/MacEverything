## 6. 问题清单

### High：全表扫描路径 page cache 30 分钟内完全丢失

- **现象**：R141 执行时 `path:/Users`=282ms → 30 分钟后 R142=2456ms（8.7x 退化）。
- **根因**：macOS 对顺序 I/O 的 page cache 策略——大块线性读取可能使用 `FADV_DONTNEED` 语义或在内存压力下优先驱逐。
- **影响**：全表扫描查询（`content:import`、`path:/Users`、`中文测试`、`dm:today`）在任何 30+ 分钟无查询后都会退化到 1-2.5 秒。
- **用户感知**：首次全表扫描查询需要 1-2.5 秒——可感知的延迟。

### Medium：系统极度空闲导致索引文件 cache 无法维持

- **932 次 skip-flush**——18 entries 永远不到 100 的阈值。
- **整个会话仅 1 次 flush**——无任何索引 I/O 活动来维持 page cache。
- **无查询用户流量**——仅性能测试 battery 的查询，间隔 30 分钟。

### Positive：Trigram postings cache 部分保持

- `.pdf` 从 R141 的 834ms 降至 R142 的 300ms——trigram 索引的 page cache 保持了 30 分钟。
- 这说明 trigram postings 文件较小且被多次随机访问——macOS 倾向于保留。

### Positive：lockWait 为零——无锁竞争

- max lockWait=8.4ms（仅 `test` 查询，可忽略）。
- 系统空闲 → 无 flush rewrite → 无锁阻塞。

## 7. 优化建议

### P0：排查 compaction rewrite 崩溃根因（持续建议）

- 下次 compaction 预计 ~8.3 小时后触发（明天 ~01:00）。
- R138 的崩溃根因仍未确认。

### P1：全表扫描 page cache 保持策略（本轮新增/升级）

- **问题升级**：从 R141 的 "P1 建议暂不实施" 升级为明确问题。证据表明全表扫描的 page cache 在 30 分钟内即丢失。
- **方案选项**（按推荐度）：
  1. **定期 madvise/prefetch**：后台线程每 5 分钟对索引的 SoA 数组区域执行 `madvise(MADV_WILLNEED)`——让 OS 知道这些页面仍有用。成本低、无常驻内存增加。
  2. **mmap + MAP_POPULATE**：索引加载时使用 mmap 而非 read，并标记 `MAP_POPULATE`。OS 会倾向于保留 mmap 页面。
  3. **mlock 热点页**：将 SoA 数组的前 N 页 mlock——保证不被驱逐。代价：增加常驻内存 ~50-100MB。
  4. **接受现状**：全表扫描本身是 O(N) 操作，冷启动 1-2.5s 在 6M 记录下属合理范围。
- **推荐方案 1 或 4**：根据用户反馈决定是否值得优化。

### P1：flush rewrite 改为 COW 方式（持续建议）

- 本轮 lockWait≈0——但系统空闲时不触发 flush，一旦恢复活跃 flush rewrite 将膨胀。

### P2：降低 compaction 阈值至 15%

- 当前 17.58% 已超 15%——如果阈值为 15% 则早已触发 compaction 清理 ~1M tombstone。

## 9. 结论

**全表扫描 page cache 30 分钟内完全丢失——3/16 >500ms（`path:/Users`=2456ms，`content:import`=1246ms），P50=221ms，lockWait≈0。** 对比 30 分钟前的 R141（`path:/Users`=282ms），全表扫描退化 8.7x——证明 macOS 在内存压力下优先驱逐顺序 I/O 的 page cache。

**Trigram 索引 cache 保持良好（`.pdf` 834→300ms，↓64%）——随机访问模式的页面被 OS 保留。** 系统持续极度空闲（932 skip-flush，18h 仅 1 次 flush），tombstone 17.58%（1.09M），距 25% compaction ~8.3 小时。

**P1 建议升级：索引文件 page cache 保持策略。** 推荐方案 1（定期 madvise prefetch）或方案 4（接受现状——1-2.5s 全表扫描在 6M 记录下属合理延迟）。根据实际用户场景决定是否投入优化。
