## 2. ⚠️ 决定性方法：会话内 15 次 `.pdf` 自然实验，排除两个触发假说

`.pdf` 候选数近似恒定（9798→9892），构成「同查询、变温度」的天然控制实验。下表含「之前 5 分钟 LLM chat 次数」与「距上次 LLM 间隔」：

|------|-------|-----------|-----------|-----------------|------|
| 13:02 | 2682 | 9,798 | — | 0 | 重启冷启 |
| 14:11 | 376 | 9,819 | 27min | 0 | 🟢 暖（无 LLM） |
| 15:12 | 6811 | 9,828 | 28min | 0 | 🔴 冷（**无 LLM**） |
| **16:09** | **18582** | 9,830 | 50min | **0** | 🔴 **严重冷（无 LLM）** |
| 16:15 | 1295 | 9,831 | 50s | 8 | 🟡 恢复中（LLM 刚发生） |
| 16:41 | 251 | 9,831 | 24min | 0 | 🟢 暖（无 LLM） |
| 18:11 | 760 | 9,890 | 25min | 0 | 🟢 暖 |
| **18:45** | **15749** | 9,890 | 25min | **0** | 🔴 **严重冷（无 LLM）** |
| 18:53 | 437 | 9,890 | 33min | 0 | 🟢 恢复 |
| **20:06** | **245** | 9,891 | **67min** | 0 | 🟢 **最暖（空闲最久、无 LLM）** |
| **20:36** | **963** | 9,892 | 124s | 8 | 🟡 **R66 轻冷（LLM 2min 前）** |

**假说一（空闲时长↑→冷）被否证**：20:06 空闲 67min（最久）反而最暖（245ms）；18:45 空闲 25min 却严重冷（15749ms）。无单调关系（**复证 R65**）。

**假说二（进程内 LLM 推理→内存压力→驱逐 SoA 页）被否证**：
- 两次**严重冷**（16:09=18582ms、18:45=15749ms）之前 5 分钟 **LLM 活动均为 0**；若 LLM 是冷因，这两次本应有 LLM 前导，事实没有。
- 两次**紧跟 LLM 突发**（16:15 间隔 50s / 20:36 间隔 124s，各 8 次 chat）均**非严重冷**（1295ms 实为 16:09 峰值后 6min 的恢复态；963ms 为轻冷）。
- ∴ 内置 AI/LLM 推理**不是冷缓存的主因**。（本轮会话 LLM 活动极频繁：128 次 chat、386 次 AI 事件、单次 infer 360–645ms；若 LLM 驱逐页成立，冷事件应远多于实测 2 次且与 LLM 对齐——并未观察到。）

**存活解释**：既非空闲、亦非进程内 LLM，则严重冷只能由**外部（跨进程）内存压力**触发——其他 App/系统的内存需求令 OS 回收 MacEverything 的文件支撑 SoA 页。此为 R65 结论经排除法的强化。

> **诚实边界**：本轮严格**否证**了空闲与 LLM 两个假说（数据充分）；「外部内存压力」是排除后的存活假说，仍缺直接的系统内存压力遥测来正面证实——**这正是 §6 建议补遥测的理由**。R66 的价值在于把候选从 3 个收敛到 1 个。

## 5. ⚠️ Tombstone 不回收的机制定位：flush 整段会话仅触发 1 次

**日志确证（强证据）**：

| 事实 | 证据 |
|------|------|
| 自动压缩已启用 | `11:12:18 Auto-compaction started (initial interval 300s)` |
| 整段会话**仅 1 次** flush | 仅 `11:12:29 Flushed v6 flat index … liveRecords=5341561 … rewrite=10331ms total=10353ms` |
| 其后**144 次跳过** | `Skipping flush — only 78 entries (threshold=100)`，首 11:17:19 末 20:41:08 |
| pending 计数恒为 **78** | 144 次跳过的 pending 值**全部=78**，从未达阈值 100 |

**机制链**：flush 是唯一重写平铺索引、丢弃 tombstone 的动作 → flush 触发条件**仅看 `pending>=100`** → pending 整段会话恒 78（<100）→ **11:12 之后 flush 永不再触发** → **tombstone 零回收，从 11:12 基线单调累积至 199,888**。

这把 R56 起反复记录的「自动压缩从不回收 tombstone」从**黑盒现象**推进为**可观测的门控缺陷**：压缩触发是**纯计数门控**，且该计数停滞在阈值下，故压缩形同空转。

> **待确认（需读 `IndexPersistence` 代码，不在本报告下结论）**：为何会话新增 ~22 万条记录（recordCount 5,341,561→5,561,920）而 pending 恒为 78？大概率「pending」只计某类待刷条目（新记录走另一路径直接落平铺），而 tombstone 回收只随**全量重写 flush** 发生。无论 pending 语义如何，**「整段会话仅 1 次 flush + tombstone 零回收」是日志铁证**。
>
> **根因级修复方向**：为 flush/压缩增加**按 tombstone 比例触发**的条件（如 tombstone% > 5% 或绝对值 > N 即强制一次压缩重写），不再纯依赖 pending 计数。低复杂度、直击根因——这是把长期 P0「tombstone 在线回收」落地的最直接抓手。
