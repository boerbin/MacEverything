## 🔴 决定性突破：tombstone 永不回收的**代码级根因**——安全阀结构性不可达

**R66 定位了 tombstone 不回收的现象（flush 整会话仅触发 1 次，pending 卡在 78<100）。R67 在源码中找到了根因，并发现它是一个比 R66 描述更深的结构性缺陷：tombstone 比例触发的整理（full compaction）安全阀被入口数阈值提前 `return` 短路，永远执行不到。** 具体见 `IndexPersistence.cpp:119-164` 的 `flush()`：第 142 行 `if (entryCount() < kCompactThreshold) return;`（kCompactThreshold=100）在前，第 159 行 `if (tombstoneRatio > kTombstoneCompactRatio) fullCompact();`（kTombstoneCompactRatio=0.25）在后。WAL entryCount 整会话冻结在 78，永远 <100，于是**第 159 行的 tombstone 安全阀是死代码**——即便 tombstone 涨到 25%，定时 auto-compaction（force=false）也绝不会触发整理。更糟的是双重缺陷：(1) 阀门不可达；(2) 阈值 25% 本身就 > R43 崩溃点 12.97%——即便阀门可达，也拦不住 R43 那种崩溃。本轮 tombstone 越过 **4.01%**（224,620），会话均速 ~22.5K/h，~25.6h 达 R43 崩溃前水平。**根因修复明确：tombstone 比例检查必须前置或与入口数阈值并联（OR），且阈值需下调到 R43 崩溃点以下。**

另一项收获：本轮采到迄今**最干净的页温度数据集**——整会话 16 次 `.pdf` 冷探针，候选数近恒定（9,798→10,015，仅 +2.2%），延迟却 112ms→18,582ms（**166×**）。这是 phase2「页温度主导、与候选数无关」的最强单一证据；且冷热程度与空闲时长无关（同样 30min 空闲既有 366ms 也有 2217ms；最长 73min 空闲反而最暖 245ms），峰后 6-8min 即恢复——坐实**外部内存压力的瞬时突发**特征。

## 2. 🔴 代码级根因：tombstone 安全阀不可达（`IndexPersistence.cpp:119-164`）

### 2.1 控制流缺陷

```cpp
void IndexPersistence::flush(const IndexMetadata& metadata, bool force) {
    {
        std::lock_guard<std::mutex> lock(walMutex_);
        if (!wal_) { ...return; }
        if (force) { ... }
        else {
            if (!wal_->isDirty()) { ...return; }
            if (wal_->entryCount() < kCompactThreshold) {   // 行142: 100
                LOG_INFO(... "only " << entryCount() << " entries");
                return;                                       // ← 早退，整会话走这里
            }
        }
    }
    // —— 以下代码在 force=false + entryCount<100 时永不执行 ——
    uint32_t totalCount = engine_->recordCount();             // 行153
    uint32_t liveCount  = engine_->liveRecordCount();
    double tombstoneRatio = (totalCount - liveCount) / totalCount;
    if (tombstoneRatio > kTombstoneCompactRatio) {            // 行159: 0.25
        fullCompact(metadata);                                // ← tombstone 安全阀（死代码）
        return;
    }
    ... // 增量 flush
}
```

**定时 auto-compaction 每 300s 调用 `flush(force=false)`。整会话 157 次全部命中行 142 早退（entryCount=78<100），第 159 行的 tombstone 比例安全阀从未被求值。** 这就是 tombstone 单调累积、自动整理「形同虚设」的根因——不是阈值没到，而是**检查顺序错误导致安全阀根本到不了**。

### 2.2 双重缺陷

| 缺陷 | 证据 | 后果 |
|------|------|------|
| ① 安全阀被入口数阈值短路 | 行 142 在行 159 之前 `return` | 25% 阀门永不触发（force=false 路径） |
| ② 阈值 25% > R43 崩溃点 12.97% | `kTombstoneCompactRatio=0.25`；R43 在 12.97% 崩溃 | 即便阀门可达，也拦不住 R43 类崩溃 |

### 2.3 flush 证据（整会话）

| 指标 | 值 |
|------|-----|
| 实际 flush（Flushed v6） | **1 次**（11:12:29，rewrite=10331ms，liveRecords=5,341,561） |
| Skipping flush | **157 次**，全部 `only 78 entries (threshold=100)` |
| pending 值分布 | 157 次**全是 78**（10 小时零变化：11:17:19 → 21:13:38） |
| flush after 11:12 | **无** |

> entryCount 冻结在 78 的成因（WAL 批量/计数语义）尚需进一步定位，但**无论 78 从何而来，修复都相同**：安全阀不能被入口数阈值短路。

### 7.1 根因修复方案（P0🔥 NEW，最高优先）

`flush(force=false)` 当前逻辑等价于「入口数<100 → 一律跳过」，使 tombstone 安全阀不可达。修复（不新增功能、不增复杂度）：

```cpp
// 先算 tombstone 比例（廉价 atomic 读）
uint32_t totalCount = engine_->recordCount();
uint32_t liveCount  = engine_->liveRecordCount();
double tombstoneRatio = totalCount > 0 ? double(totalCount - liveCount) / totalCount : 0.0;
bool tombstonePressure = tombstoneRatio > kTombstoneCompactRatio;

// 入口数阈值与 tombstone 压力并联：任一满足即继续
if (!force && (!wal_->isDirty() ||
    (wal_->entryCount() < kCompactThreshold && !tombstonePressure))) {
    return;  // 仅在「入口数低 且 无 tombstone 压力」时才跳过
}
```

并将 `kTombstoneCompactRatio` 从 0.25 下调至 **0.10**（低于 R43 的 12.97% 崩溃点，留安全裕度）。
- **验收**：构造 >10% tombstone 的索引，等待一个 auto-compaction 周期（300s），日志应出现 `Tombstone ratio ...% > 10% — triggering full compaction` 且 tombstone 归零；现有测试不回归。
- **风险/回滚**：fullCompact 是 10s 级全量重写（持锁），需配合 P0 无锁 flush 或限流，避免压缩瞬间阻塞查询。回滚仅需还原阈值与判断式。
