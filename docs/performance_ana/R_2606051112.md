## 6. 问题清单

### High：flush rewrite 5-13 秒——lockWait 风暴随时可能重现

- 本轮 lockWait=0 是运气——查询恰好避开了 5-13 秒的 flush rewrite 窗口。
- **13.2 秒 rewrite 期间的任何查询都会被阻塞 >10 秒。**
- **R134 的 70 秒灾难就是同类问题的极端情况。**
- **P0 建议（COW flush）仍然是唯一根本解决方案。**

### Medium：tombstone 15.43%——距 25% compaction 还需 ~635K

- 按当前风暴增速 8,942/min：**~71 分钟后触发（~12:23）。**
- **之前所有报告的 "15% compaction 预估"均基于错误假设——实际阈值为 25%。**
- **tombstone 将继续堆积至 25% → flush rewrite 继续恶化 → lockWait 风险持续升高。**

### Medium：`path:/Users`=427ms——page cache 竞争

- 从 R136 的 198ms 上升至 427ms（↑116%）——phase2=417ms 说明全表扫描 I/O 成本大增。
- **原因**：事件风暴 → 大量文件元数据被读写 → page cache 被挤占 → 全表扫描需要更多磁盘 I/O。
- **compaction 后会改善**——recordCount 减少 ~25% → 扫描数据量减少 → 即使 page cache 不变也更快。

### 正面：查询引擎本身性能良好

- 0/16 >500ms，lockWait=0。
- P50=72.5ms，Max=427ms——在事件风暴+flush rewrite 恶化的背景下仍然达标。
- **"幸运地"避开了 flush 窗口——但系统架构不应依赖运气。**

## 7. 优化建议

### P0：flush rewrite 改为 COW 方式（优先级最高，不变）

- **注意：compaction 已经是 COW 模式（日志确认 "COW compaction Phase 2/3"），但 flush rewrite 仍然持有写锁。**
- **flush rewrite 是目前唯一不是 COW 的 I/O 密集操作。**
- R134（70s）、R135（10s, 443ms lockWait）、R137（13s, lockWait=0 纯靠运气）持续证明需求。
- **COW flush 方案**：rewrite 写入临时文件（不持锁）→ 完成后原子 rename（持锁 <1ms）。

### P1：降低 Compaction 阈值至 15%（修正后的建议）

- **当前 25% 阈值过高**——从 compaction 后的 ~0% 到下次触发的 25%，tombstone 会堆积至 recordCount 的 1/4。
- **25% tombstone 意味着 flush rewrite 需要写入比实际有效数据多 33% 的数据量。**
- **建议降低至 15%**：
  - tombstone 堆积上限减少 40%（25% → 15%）。
  - flush rewrite 数据量减少——即使在最坏情况下也仅比有效数据多 18%（vs 当前的 33%）。
  - compaction 更频繁但每次更快（处理更少数据）。

### P2：flush rewrite 时间告警

- 当 rewrite >10 秒时记录 WARN 日志。
- 可作为 lockWait 风险的早期预警指标。

**0/16 >500ms，lockWait=0——查询性能完全恢复。但 tombstone 飙升至 15.43%（首次突破百万，1,052K），flush rewrite 暴涨至 5-13 秒。** 本轮查询恰好避开 flush 窗口，因此无 lockWait——但这是运气，13 秒 rewrite 期间的任何查询都会被严重阻塞。
