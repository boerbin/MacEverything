## 6. 问题清单

### Critical：服务持续不可用，所有 HTTP 请求 connection refused

- 证据：16 个 battery query、status、floor/reprobe 和额外 HTTP 检查全部 connection refused；进程检查未列出 MacEverything。
- 影响：搜索功能完全不可用，用户无法执行任何查询。
- 根因判断：问题从 16:42 compaction 窗口后的 timeout/refused 延续到 17:12、17:42、18:11、18:41、19:11、19:41、20:12、20:41、21:12、21:42、22:12，服务没有自动恢复。
- 优先级：最高。

### Critical：compaction done 后没有服务恢复证据

- 证据：最新日志停在 `COW compaction done`，之后没有 `Log session started`、HTTP server ready、server stop、service restart、health check 或错误记录。
- 影响：即使 compaction 数据层流程结束，服务层仍不可用。
- 根因判断：compaction 生命周期与 HTTP 服务生命周期之间缺少恢复保障和可观测性。

### High：日志无法解释进程退出或 HTTP server 停止

- 证据：`WARN=0 ERROR=0`，但外部请求 connection refused 且进程不存在。
- 影响：无法判断是 crash、正常退出、server stop、端口绑定失败还是外部 kill。
- 根因判断：关键 lifecycle/fatal observability 缺失。

### High：full compaction 与在线服务隔离不足

- 证据：R_2606011642 显示 compaction Phase 2/3 附近出现 `.pdf=6841ms`、`*.swift=3645ms`、`main.cpp=1331ms`，之后 probe timeout/refused；本轮仍 refused。
- 影响：维护任务会演变为用户可见的服务级故障。
- 根因判断：full compaction 对查询、flush、HTTP server 生命周期和资源竞争没有足够隔离。

### Medium：report parser 指标语义仍需拆分

- 证据：日志明确存在 COW compaction，但汇总仍显示 `RECLAIM=0`。
- 影响：读者可能误解为没有执行回收或压缩动作。
- 根因判断：`RECLAIM` 指标与 COW compaction 不是同一语义，应拆分命名。

## 7. 优化建议

### P0：优先恢复服务并补齐生命周期观测

下一步不应继续做常规延迟对比，而应定位服务为何不存在：

1. 检查 macOS crash report、Console log、launch/terminate 记录。
2. 在 app start、HTTP server start/stop、ServiceEngine start/stop、applicationWillTerminate、uncaught exception、fatal signal 处写日志。
3. 在 compaction start、Phase 2、Phase 3、done 后记录 HTTP server 是否仍监听 `19860`。
4. `/api/status` 应成为轻量 health endpoint，能区分 engine ready、compacting、degraded、server shutting down。

验收标准：再次出现 connection refused 时，日志能明确说明进程退出、server 停止、端口绑定失败或外部终止，而不是只能依赖外部观察。

### P0：compaction 完成后必须保持或恢复 HTTP 服务

建议在 compaction done 后增加显式一致性和 health 检查：

- 验证 SearchEngine snapshot 已发布；
- 验证 HTTP handler 仍可访问 engine；
- 验证监听 socket 仍绑定 `19860`；
- compaction 失败时回滚到旧 snapshot；
- 若服务决定退出，必须记录退出原因。

验收标准：full compaction 后 `curl http://localhost:19860/api/status` 持续返回，query battery 能继续执行。

### P0：将 full compaction 改为可中断、可限速、可恢复

当前一次处理 7.3M records 的 full compaction 风险过高。建议：

- 分批 compact，避免一次性大窗口；
- 限制 CPU/I/O，避免抢占 query 和 flush；
- 每个阶段检查 cancellation 与 health；
- Phase 2 使用旧 snapshot 服务查询；
- Phase 3 swap 必须是毫秒级短锁；
- replay adds/deletes 不应阻塞 HTTP accept loop。

验收标准：compaction 期间 `/api/status`、`q=x` 和常见查询不 timeout、不 refused。

### P1：前移 tombstone debt 治理

25% 触发点已经被验证过晚。建议：

- 8–10% tombstone ratio 开始渐进 reclaim；
- 使用 debt score 组合 tombstone ratio、tombstone 绝对量、flush GE10、full-scan p95、skipflush 增量；
- 避免积累到 180万+ tombstones 后才进行 20 分钟级维护。

验收标准：tombstone ratio 不再接近 25%，且不再出现单次 20 分钟 full compaction。

### P1：拆分 compaction/reclaim 指标

建议报告脚本拆分：

- `COMPACTION_TRIGGER`
- `COMPACTION_PHASE2`
- `COMPACTION_SWAP`
- `COMPACTION_DONE`
- `RECLAIM_LEGACY` 或移除模糊的 `RECLAIM`

这样后续报告可以避免“COW compaction 已执行但 RECLAIM=0”的语义冲突。

## 8. 下一轮重点

1. 先恢复或重启 MacEverything，并确认 `http://localhost:19860/api/status` 可用。
2. 检查 macOS crash report、Console log 或 app lifecycle log，定位进程为何不存在。
3. 服务恢复后读取 status，确认 compaction 后 `recordCount/liveRecordCount/tombstoneRatio` 是否已经回落。
4. 再运行固定 query battery，比较 compaction 后 full-scan floor 是否改善。
5. 如果服务再次在 compaction 后不可用，应暂停常规性能优化，优先修复服务生命周期与 compaction recovery。

本轮 22:12 复核显示 MacEverything HTTP 服务仍持续不可用：所有 query、status、floor、reprobe 和额外 HTTP 检查均 connection refused，进程检查也没有发现 MacEverything。日志没有新增查询、启动或错误记录，最新事件仍停留在 16:57:52 的 COW compaction done。

因此当前最高优先级仍是服务可用性与可观测性：先补齐进程/HTTP server 生命周期日志、崩溃诊断和 compaction recovery，再回到 query 延迟优化。
