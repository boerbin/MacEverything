### 崩溃原因分析

| 假设 | 证据 | 可能性 |

| **信号被外部进程杀死** | 系统资源管理器（jetsam）杀死高内存进程 | 低-中 |

- **COW compaction Phase 2 + Phase 3 成功完成**——数据已在内存中正确压缩和交换。

- **没有 crash report（~/Library/Logs/DiagnosticReports/ 中无 MacEverything 条目）**——可能是被 jetsam 杀死或未生成 crash log。

- **根因推测**：compaction rewrite 需要将压缩后的 5.77M 记录完整写入新索引文件——在事件风暴期间（recordCount=7.7M, flush rewrite 已达 13s），这个步骤可能需要大量内存和磁盘 I/O。

## 7. 优化建议

### P0（新增）：排查 compaction rewrite 崩溃原因

- **这是首次观察到的进程崩溃——需要根因分析。**
- **建议**：
  1. 在 compaction rewrite 前后添加详细日志（记录内存使用、磁盘空间）。
  2. 添加 signal handler 捕获 SIGKILL/SIGTERM 并记录。
  3. 检查 rewrite 期间的内存峰值——如果 rewrite 需要同时持有旧索引和新索引，内存可能翻倍。
  4. 考虑 rewrite 分块写入而非一次性构建完整索引。

### P0（持续）：flush rewrite 改为 COW 方式

- 崩溃事件进一步证明了 I/O 密集操作的风险。
- **COW flush 方案不仅消除 lockWait，还减少了 rewrite 失败时的影响范围。**

### P1：降低 compaction 阈值至 15%

- **25% 阈值过高**——导致 tombstone 大量堆积（本次高达 1.05M）→ flush rewrite 数据量膨胀 → 间接导致崩溃。
- **15% 阈值将使 compaction 更频繁但每次处理更少数据 → rewrite 更快、更安全。**

### P2：compaction rewrite 添加 crash-safe 机制

- 当前 rewrite 未完成即崩溃 → 回退至旧索引 → 需要全量扫描重建。
- **建议**：rewrite 完成后先 fsync 再 rename（确保 crash-safe），失败时自动触发重试而非回退。
