## 2. 执行摘要

**Flush I/O 风暴再现——rewrite 从 3-4 秒飙升至 105 秒。9/16 查询 >500ms。lockWait=0 但 GCD dispatch 延迟成为新的主导瓶颈。** tombstone 仅 0.97%（compaction 后稳态），但 flush rewrite 时间异常膨胀。

**本轮揭示一个关键新发现：性能退化与 tombstone 无关——flush I/O 独立于 tombstone 成为瓶颈。** R109 的历史最佳（P50=14ms）仅维持了 1 轮。

- **tombstone 仅 0.97%，文件大小变化极小**——rewrite 膨胀不是 tombstone 引起的。
- **原因推测**：
  1. **磁盘 I/O 争用**：flush 高频运行（30 分钟内 +51 次），与系统后台 I/O（Spotlight、Time Machine）叠加。
  2. **flush 频率过高导致磁盘排队**：每次 flush 写 ~1.7GB，30 分钟内 51 次 = ~87GB 写入——**即使 tombstone 清零后磁盘仍在超负荷运转**。
  3. **SSD 写入放大或温度降速**：持续高频大量写入可能触发 SSD 控制器降速。

- **对比 R109**：`x`=2.2ms（同样 short-query-cache）——**1,698 倍退化**。
- **原因**：GCD 线程池被 flush I/O 线程占用——查询在 GCD 队列中等待 3.7 秒才被调度执行。

### Flush rewrite 膨胀的根因假设

1. **SSD 写入放大**：142 分钟内写入 ~257GB，SSD 控制器可能触发 TRIM 和垃圾回收，导致写入延迟急剧上升。
2. **操作系统页面缓存压力**：每次重写 ~1.7GB 文件会污染 macOS 的 unified buffer cache，迫使系统频繁换页。
3. **磁盘 I/O 调度器拥塞**：flush 写入和查询读取竞争 I/O 调度队列——高频 flush 导致查询 I/O 请求被延迟。

## 6. 问题清单

### Critical：Flush I/O 风暴独立于 tombstone——新的系统性瓶颈

- **tombstone 仅 0.97% 但 flush rewrite 从 3 秒膨胀至 105 秒。**
- **136 次 flush 在 142 分钟内，累计写入 ~257GB。**
- **flush 是所有性能问题的根因**——不是 tombstone，不是 lockWait，而是 flush I/O 本身。
- **flush 导致**：
  1. GCD dispatch 延迟（3,735ms for `x`，phase2=0ms）
  2. phase2 I/O 阻塞（`hello world` phase2 从 3ms→1,945ms）
  3. 磁盘带宽耗尽

### Critical：Flush 频率过高——30 分钟 51 次

- 平均 35 秒/次——**几乎连续不断地在重写文件**。
- 每次重写 ~1.7GB——**磁盘利用率接近 100%**。
- **R109 之所以优秀**，是因为恰好在 flush 空闲窗口执行查询——但这是运气，不是系统行为。

### High：GCD 线程池被 flush I/O 阻塞

- 8/16 查询有 >500ms 的 GCD dispatch 开销。
- GCD 线程池的工作线程被 flush I/O 操作占用——查询任务在队列中排队等待。
- **需要将 flush I/O 隔离到独立线程/队列**，避免与查询 GCD 竞争。

### 正面：tombstone 0.97%——compaction 效果持续

- compaction 后 45 分钟，tombstone 仅增至 0.97%——增速 ~1,260/min（正常稳态水平）。
- **25% 阈值 compaction 证明有效**——tombstone 不再是瓶颈。
- **lockWait=0**——锁竞争已完全消除。

## 7. 优化建议

### P0 紧急：大幅降低 Flush 频率

- **当前**：每 ~35 秒 flush 一次，每次重写 ~1.7GB。
- **方案 A**：增加最小 flush 间隔至 5-10 分钟——减少 80-90% 的 flush I/O。
- **方案 B**：基于 pending changes 数量触发——仅当 pending changes 超过 10,000 条时 flush（当前阈值 100 太低）。
- **方案 C**：增量 flush——仅追加新/修改的记录到文件末尾，避免全量重写。
- **预期收益**：消除 GCD dispatch 延迟，恢复 R109 水平的性能。

### P0 紧急：Flush I/O 隔离

- **方案**：flush 使用独立的低优先级 I/O 队列（`DISPATCH_QUEUE_PRIORITY_BACKGROUND`），避免与查询竞争 GCD 线程和磁盘带宽。
- **预期收益**：即使 flush 在执行，查询也能获得足够的 I/O 和 CPU 资源。

### P1：COW flush（与 COW compaction 类似）

- **方案**：flush 写入临时文件后原子替换——flush 期间查询继续使用旧文件，无 I/O 竞争。

### P2：Flush 进度监控

- 增加 flush I/O 监控指标——rewrite 时间、磁盘利用率、I/O 队列深度。

## 8. 下一轮重点

1. flush rewrite 时间是否继续膨胀（105 秒是否为峰值）。
2. tombstone 增速是否维持在 ~1,260/min 稳态水平。
3. GCD dispatch 延迟是否在 flush 间隙恢复正常。
4. SKIPFLUSH 是否继续增加（flush 开始自我限流）。

## 9. 结论

**Flush I/O 风暴再现——rewrite 从 3-4 秒飙升至 105 秒（26 倍），9/16 查询 >500ms。** tombstone 仅 0.97%（compaction 后稳态），lockWait=0（全部 16 查询），但 **GCD dispatch 延迟成为新的主导瓶颈**——`x`=3,735ms（short-query-cache 命中，phase2=0ms，全部为 GCD 等待），`README`=2,536ms（GCD 开销 2,212ms），`hello world`=3,282ms。P50=647ms（R109 的 14ms 退化 45 倍），Max=3,735ms。**136 次 flush 在 142 分钟内，累计写入 ~257GB——磁盘 I/O 预算被 flush 完全耗尽。** 7 个正常查询全部 <400ms——**查询引擎本身在低 tombstone 下性能优秀，瓶颈完全来自 flush I/O**。**R109 的历史最佳是 flush 间隙的运气，不是系统稳态行为。必须大幅降低 flush 频率（从 35 秒/次提高到 5-10 分钟/次）并隔离 flush I/O 到后台队列，才能实现真正稳定的高性能。**
