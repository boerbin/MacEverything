## 6. 问题清单

### P0：前台尾部重新接近 500ms

- 证据：`中文测试`=449.2ms，phase2=448.5ms；`path:/Users`=387.9ms，phase2=379.2ms。
- 影响：虽然未正式超过 500ms，但已经进入用户明显可感知区间，下一轮或后台状态变化时很容易越线。
- 判断：lockWait=0ms，瓶颈主要在 phase2 的 linear-gcd 扫描阶段。

### P0：tombstone 在 14% 以上继续上行

- 证据：tombstone=898,964（14.48%），较上一轮增加 7,604。
- 影响：无效记录比例继续升高，会放大扫描成本、索引重写成本与 compaction 压力。
- 判断：连续多轮位于 14% 以上并继续增长，compaction/清理策略仍未有效压低 tombstone。

### P0：new session 内 flush 已累积到 20 次且无退避

- 证据：`FLUSH=20`，较上一轮 +6；`SKIPFLUSH=0`；session 最大 flush total=6164ms，最新 flush total=3472ms。
- 影响：完整重写继续制造 I/O 与 page-cache 干扰，并可能导致本轮 P50/P90 明显抬升。

### P0：scan/filter 路径总和显著上升

- 证据：扫描/过滤路径总和从 951.3ms 升至 1205.1ms；`dm:today`=120.9ms、`content:import`=195.7ms、`path:/Users`=387.9ms、`中文测试`=449.2ms。
- 影响：尾部不只是单个查询异常，而是 scan/filter 系列整体抬升。

### P1：trigram 路径仍有中位以上波动

- 证据：`hello world`=146.0ms，`abc def ghi jkl mno pqr`=82.7ms，`.pdf`=41.0ms。
- 影响：trigram 当前未超标，但 postings 读取、候选处理或 page-cache 状态仍可能把部分查询推到 100ms+。

## 7. 优化建议

### P0：立即提前或分段 compaction

- 以 tombstone 率 14%+ 作为明确触发信号，不再等待更高阈值。
- 结合绝对 tombstone 数、segment tombstone 率和 flush rewrite 成本触发局部 compaction。
- 优先处理 tombstone 密集 segment，避免 scan/filter 路径继续扫描大量无效记录。
- 验收：tombstone 率从 14.48% 回落，`中文测试`、`path:/Users`、`content:import` 稳定 <200ms。

### P0：flush 改为增量/COW 页写入

- 将 stable segment 与 delta segment 分离，常规 flush 只追加或替换小段 delta。
- 大段合并放到后台低优先级任务，不与前台查询争抢热页或持锁窗口。
- 验收：常规 flush total <200ms，新 session 不再出现 3-6s 级完整 rewrite。

### P0：增加 flush I/O 压力退避和前台保护

- 当最近 flush 超过阈值时，提高下一次 flush 间隔、降低 batch 频率，或前台查询活跃时推迟大 flush。
- 持久化线程使用低 QoS，并评估大顺序写的 `F_NOCACHE`/同类策略，减少对搜索热页的冲刷。
- 验收：`SKIPFLUSH` 不再长期为 0，3-6s flush 后不再出现 400ms+ linear-gcd 尾部。

### P0：为 advanced-linear-gcd 与 pure-filter 增加轻量剪枝

- 对中文、路径、content/filter 类查询记录扫描记录数、tombstone 跳过数和 segment 分布。
- 评估轻量字符 n-gram、路径分段索引、预过滤位图或 segment-level skip list，以减少无结果或低选择性查询的全量扫描。
- 要求保持内存增长可控，优先使用压缩或按需结构，不引入大常驻索引。
- 验收：`中文测试` 不再接近 500ms，`path:/Users` 与 `content:import` 稳定低于 200ms。

### P1：细分 trigram/postings 路径

- 对 `advanced-trigram` 记录 postings 读取、候选交并、候选评分、路径加载、结果组装、page-cache miss 近似指标。
- 重点解释 `hello world` 继续保持 100ms+ 的成本来源。
- 验收：trigram 查询在 flush 后仍稳定 <100ms，或至少能解释每个阶段的成本。

### P1：拆分 top-level query timing

- 对所有路径增加 queueWait、phase2、candidate materialization、path/file metadata load、sort/rank、result assembly、HTTP serialization/write 等阶段耗时。
- 验收：`queryTimeMs - phase2Ms - lockWaitMs` 不再是不可解释的大黑盒。
