## 6. 问题清单

### P0：前台尾部重新接近 500ms

- 证据：`中文测试`=415.1ms，phase2=414.4ms；`path:/Users`=311.5ms，phase2=287.1ms。
- 影响：虽然仍未超过 500ms，但最高项已从 356.1ms 回升到 415.1ms，用户可感知风险重新上升。
- 判断：lockWait=0ms，瓶颈主要在 phase2 的 linear-gcd 扫描阶段。

### P0：tombstone 突破 910k 且继续上行

- 证据：tombstone=911,770（14.65%），较上一轮增加 6,013。
- 影响：无效记录比例继续升高，会放大扫描成本、索引重写成本与 compaction 压力。
- 判断：连续多轮 tombstone 上行，说明 compaction/清理策略仍未追上更新与删除积累速度。

### P0：new session 内 flush 已累积到 32 次且无退避

- 证据：`FLUSH=32`，较上一轮 +6；`SKIPFLUSH=0`；session 最大 flush total=6164ms。
- 影响：完整重写持续制造 I/O 与 page-cache 干扰，容易让 linear-gcd、pure-filter、trigram 在不同采样点出现尾部抬升。
- 判断：flush 频率继续按固定节奏累积，未看到对 3-6s rewrite 的保护机制。

### P0：scan/filter 路径总和重新上升

- 证据：扫描/过滤路径总和从 910.9ms 升至 1045.6ms；`dm:today`=92.8ms、`content:import`=176.8ms、`path:/Users`=311.5ms、`中文测试`=415.1ms。
- 影响：尾部不是单个查询孤立抖动，pure-filter 与 linear-gcd 系列整体再次抬升。

### P1：trigram 仍有 100ms+ 尾部

- 证据：`hello world`=121.6ms，`abc def ghi jkl mno pqr`=49.5ms，`.pdf`=35.1ms。
- 影响：trigram 多数查询仍健康，但部分多词查询仍会进入 100ms+，需要进一步拆分 postings 与候选处理成本。

## 7. 优化建议

### P0：立即提前或分段 compaction

- 以 tombstone 率 14%+ 或绝对 tombstone 900k+ 作为明确触发信号，不再等待更高阈值。
- 结合 segment tombstone 率和 flush rewrite 成本触发局部 compaction。
- 优先处理 tombstone 密集 segment，避免 scan/filter 路径继续扫描大量无效记录。
- 验收：tombstone 率从 14.65% 回落，`中文测试`、`path:/Users`、`content:import` 稳定 <200ms。

### P0：flush 改为增量/COW 页写入

- 将 stable segment 与 delta segment 分离，常规 flush 只追加或替换小段 delta。
- 大段合并放到后台低优先级任务，不与前台查询争抢热页或持锁窗口。
- 验收：常规 flush total <200ms，新 session 不再出现 3-6s 级完整 rewrite。

### P0：增加 flush I/O 压力退避和前台保护

- 当最近 flush 超过阈值时，提高下一次 flush 间隔、降低 batch 频率，或前台查询活跃时推迟大 flush。
- 持久化线程使用低 QoS，并评估大顺序写的 `F_NOCACHE`/同类策略，减少对搜索热页的冲刷。
- 验收：`SKIPFLUSH` 不再长期为 0，3-6s flush 后不再出现 400ms+ linear-gcd 尾部。

### P0：为 advanced-linear-gcd 与 pure-filter 增加轻量剪枝

- 对中文、路径、content/filter 类查询记录扫描记录数、tombstone 跳过数和 segment 分布。
- 评估轻量字符 n-gram、路径分段索引、预过滤位图或 segment-level skip list，以减少无结果或低选择性查询的全量扫描。
- 要求保持内存增长可控，优先使用压缩或按需结构，不引入大常驻索引。
- 验收：`中文测试` 不再接近 500ms，`path:/Users` 与 `content:import` 稳定低于 200ms。

### P1：细分 trigram/postings 路径

- 对 `advanced-trigram` 记录 postings 读取、候选交并、候选评分、路径加载、结果组装、page-cache miss 近似指标。
- 重点解释 `hello world` 持续 100ms+ 的成本来源。
- 验收：trigram 查询在 flush 后仍稳定 <100ms，或至少能解释每个阶段的成本。

### P1：补充 scan/filter 与 top-level timing

- 对 all-scan、pure-filter、linear-gcd 记录扫描记录数、跳过 tombstone 数、命中 live 数、segment 数、metadata 加载耗时和结果组装耗时。
- 对所有路径增加 queueWait、phase2、candidate materialization、path/file metadata load、sort/rank、HTTP serialization/write 等阶段耗时。
- 验收：`queryTimeMs - phase2Ms - lockWaitMs` 不再是不可解释的大黑盒，scan/filter 尾部能归因到具体阶段。

## 9. 结论

**本轮没有 >500ms 查询，但 Max=415.1ms、P90≈176.8ms，前台尾部较 14:18 再次抬升。** `中文测试` 和 `path:/Users` 仍是最主要尾部，耗时几乎全部来自 phase2 linear-gcd 扫描；pure-filter 的 `content:import` 也回升到 176.8ms。

**后台根因继续恶化：tombstone=911,770（14.65%），新 session `FLUSH=32`，最大 flush total=6164ms，且 `SKIPFLUSH=0`。** 下一步仍应优先推进提前/分段 compaction、增量/COW flush、flush 前台保护/退避、advanced-linear-gcd/pure-filter 剪枝，以及 trigram 与 scan/filter/top-level timing 拆分。
