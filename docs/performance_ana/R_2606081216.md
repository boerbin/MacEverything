**关键发现**：candidates 数量与冷热无关！
- `.pdf`(9.8K candidates)=7193ms，但 `test`(116K candidates)=40ms。
- 决定因素是 postings 页面在 page cache 中的位置，而非 postings 数量。

**成因假说**：系统发生了大规模**顺序 I/O 操作**（Time Machine 备份、大文件拷贝、Xcode 索引等），导致：
1. **page cache LRU 大量淘汰 trigram postings 中的"冷区域"页面**。
2. **顺序 I/O 自身的 readahead 与全扫描路径（SoA/linear）的 readahead 竞争有利**——全扫描反而改善。
3. **`README`/`test`/`MacEverything` 的 postings 区域恰好在 page cache "热区域"**——未被淘汰。

## 6. 问题清单

### 观察项：选择性 trigram 页面淘汰（新模式！）

- **现象**：特定 trigram 查询灾难性劣化（7193ms），同时其他 trigram 查询保持极佳（7ms），全扫描路径反而改善。
- **根因**：系统顺序 I/O 操作选择性淘汰 trigram postings 文件中的特定区域。随机访问 postings 的查询被灾难性命中，而全扫描路径因 readahead 竞争有利反而受益。
- **影响范围**：仅影响 postings 冷区域对应的查询（.pdf, hello world, *.swift, ext:cpp）。
- **恢复预期**：1 轮 battery 可预热受影响区域的部分 postings，但完全恢复取决于系统 I/O 压力是否消退。

### `.pdf`=7193ms——系列绝对最高

- **此前最高**：`test`=2217ms（R176 睡眠/唤醒）。
- **本轮 7193ms 是 R176 最高值的 3.2x。**
- **原因**：R176 是均匀冷启动（所有 postings 冷），本轮是选择性冷态+磁盘带宽被顺序 I/O 占据——随机 I/O 延迟被极端放大。

### tombstone 22.62%——距阈值缩短

- **增速 445/min（持续减速），距 25% 约 14-16 小时。**

## 7. 优化建议

### P0：排查 compaction rewrite 崩溃根因（紧迫）

- tombstone 22.62%（1.49M），距 25% 约 14-16 小时。

### P1：flush rewrite 改为 COW 方式（持续建议）

- 本轮 lockWait≈0——非本轮问题，但 R179=64ms 已证明极端情况存在。

### P2：唤醒预热策略 → **升级为通用热区维护策略**

- **本轮数据揭示**：不仅唤醒后需要预热，日间系统 I/O 也会选择性淘汰 trigram postings。
- **建议扩展**：维护高频查询的 postings 热区列表，定期 `madvise(MADV_WILLNEED)` 保持热态。
- **不仅限于唤醒场景——日间任何时候都可能发生选择性淘汰。**

### P3（新）：trigram postings 文件布局优化

- **当前**：postings 按 trigram ID 顺序存储。
- **问题**：高频查询的 postings 分散在文件不同区域——被选择性淘汰时无法通过 readahead 恢复。
- **建议**：将高频 trigram 的 postings 聚集到文件头部——使 readahead 一次性覆盖高频区域，提高 page cache 粘性。
- **代价**：compaction 时需重组 postings 文件——可与 P0 合并实施。

## 9. 结论

**选择性 trigram 灾难——`.pdf`=7193ms（系列绝对最高），5/16 >500ms，但全扫描反而改善至 733ms，lockWait≈0。** 这是一种全新的性能退化模式：系统顺序 I/O 操作（可能是 Time Machine/Spotlight/大文件操作）选择性淘汰 trigram postings 文件中的特定区域，同时全扫描路径因 readahead 竞争有利反而受益。结果是极端的两极分化——同为 trigram 路径，`MacEverything`=7ms 而 `.pdf`=7193ms（1106x 差距）。

**核心发现**：trigram 性能的决定因素不是 candidates 数量，而是 postings 页面在 page cache 中的冷热状态。这取决于 postings 文件中的物理位置是否与系统 I/O 活跃区域重叠。建议 P3 新增 postings 布局优化——将高频 postings 聚集到文件头部以提高 page cache 粘性。tombstone 22.62%，增速持续减速至 445/min，距 25% 约 14-16 小时。P0 compaction 修复持续紧迫。
