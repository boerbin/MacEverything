## 2. 事件分析：Flush-Phase 对齐

### 锁等待时间序列

查询按顺序执行（每个间隔 0.3s），锁等待呈递减模式：

| 顺序 | 查询 | lockMs | 解释 |
|------|------|-------:|------|
| 1 | x | >10,000 | **超时** — flush 正在进行 |
| 2 | .pdf | >10,000 | **超时** — flush 仍在进行 |
| 3 | main.cpp | 0 | flush 完成，但缓存被污染 |
| 4 | *.swift | **173** | **第二次 flush** 开始 |
| 5 | ext:cpp | **1280** | 等待第二次 flush 完成 |
| 6 | size:>100m | **104** | 第二次 flush 尾部 |
| 7 | hello world | **17** | 第二次 flush 结束 |
| 8-16 | 后续 | 0 | 无锁等待 |

**重建事件时间线**:
1. **T+0s**: 查询 `x` 发起，遭遇正在进行的 flush → 等待 >10s → 超时
2. **T+0.3s**: 查询 `.pdf` 同样超时
3. **T+10s~**: flush 完成，`main.cpp` 无需等锁（但 trigramMs=75ms 说明缓存被 flush I/O 污染）
4. **T+10.5s**: 第二次 flush 触发，`*.swift` 等待 173ms
5. **T+11s**: `ext:cpp` 在第二次 flush 期间等待 1280ms
6. **T+12.5s**: flush 即将完成，`size:>100m` 等 104ms，`hello world` 等 17ms
7. **T+13s~**: flush 完成，后续查询正常

### 关键发现

**这是一次"双 flush"事件** — 测试窗口内恰好撞上两次连续的 flush 操作：
- 第一次 flush：持续 >10 秒（导致 x、.pdf 超时）
- 第二次 flush：持续 ~1.5 秒（导致 ext:cpp 1280ms）

第一次 flush 的 >10 秒持续时间极为异常。正常 flush 写入 620 万+ 记录的 v6 flat index 通常在 1-3 秒内完成。可能原因：
1. **磁盘 I/O 竞争**: 高峰 III 期间大量文件变更导致磁盘带宽饱和
2. **Index 文件增大**: 620 万→627 万记录，index 文件已达到 ~1GB+
3. **脏页回写堆积**: macOS 的 unified buffer cache 在高 I/O 时延迟回写

## 6. 优化建议（紧迫性提升）

| 优先级 | 项目 | 预期效果 | 紧迫性 |
|--------|------|----------|--------|
| **P0** | **无锁快照刷写** | **消除 >10s 锁等待和超时** | **⚠️ 极其紧急（已导致查询超时）** |
| **P0** | Tombstone compaction | 减少 flush 数据量 30%+ | **极其紧急** |
| P0 | 增量刷写替代全量刷写 | 将单次 flush 从 627 万记录降至 delta | 紧急（新增） |
| P1 | CJK trigram/path 索引化 | 消除线性回退 | 中 |
| P1 | Trigram bucket 缓存预热 | 减少 flush 后缓存污染 | 中 |

**优先级重大调整**:
- **无锁快照刷写**从"高"提升至**极其紧急** — flush 已导致查询超时，生产环境不可接受
- **新增 P0: 增量刷写** — 全量写入 627 万记录是 >10s flush 的根本原因。增量刷写（只写变更的记录）可将 flush 时间从秒级降至毫秒级
