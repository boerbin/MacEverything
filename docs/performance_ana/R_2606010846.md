## 10. P0 优化建议（7 条 + 资源平衡说明）

1. **阀门下调 0.25 → 8–10%**（`IndexPersistence.cpp:159`）：解锁 runtime reclaim。墓碑六连涨至 21.88% 而 reclaim 恒为 0，阀门是墓碑只增不减的直接闸门。
2. **无锁快照刷新 / 读写解耦（并列 TOP）**：本轮损伤**硬化为平台**（§2 W2 劣于 W1、§3 反复探测不回落），是 6 轮来对"查询全程持锁 × 后台重写串行化争用"最强的证据。应让查询读取不可变快照、flush 通过指针交换发布新版本。
3. **按簇密度的风暴护栏**（滚动窗口背靠背计数，而非单次时长）：08:36–08:38 的 4×≥5s 簇直接先于查询破窗。护栏应基于"窗口内重写次数"。
4. **全扫尾部护栏（string 线性层）**：path/中文/content 卡在 200–265ms 平台。为 linear-gcd 路径设预算/分段让出，避免与 flush 叠加放大到 700ms+。
5. **dm 列驻留 / page-state**：dm 干净时 58ms，但并发 flush 下飙升（W2 132ms）。固定列页驻留，降低并发抖动。
6. **trigram 冷缓存预热 / 驻留**：本轮 trigram 健康（<80ms），但历轮冷点在查询间轮转。周期性预热保持驻留。
7. **查询超时 / 熔断**：本轮两次重写 15.9min / 34.4min。与此类重写并发的查询需 deadline + fail-fast，避免无界等待。

**资源平衡说明**：7 条全部是 **I/O 调度 / 并发控制**类改动（阀门阈值、快照指针交换、滚动计数器、deadline 计时器），**无一以内存换计算或以计算换内存**。其中 #2 无锁快照在 flush 期间额外占用"一个索引指针版本"的瞬时内存（有界、交换后即释放），相对其消除的分钟级停顿可忽略；#3/#7 为 O(1) 计数器/计时器。**未引入大内存表，未新增重计算**——内存与计算成本平衡。
