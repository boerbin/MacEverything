## 8. 问题清单

### Critical：25% full compaction 期间服务进入不可用状态

- 证据：probe 后半段全部 timeout 或 connection refused；额外 HTTP status/search 检查均 connection refused；进程列表未发现 MacEverything。
- 影响：用户无法通过 HTTP 服务查询，功能不可用。
- 根因判断：与 25% COW compaction 时间窗高度相关，但现有日志没有 crash/error，需要补充退出原因、崩溃日志或进程生命周期日志。
- 优先级：最高。

### Critical：COW compaction 与查询路径耦合，导致秒级查询尾延迟

- 证据：compaction Phase 2/3 附近 `.pdf=6841ms`、`*.swift=3645ms`、`main.cpp=1331ms`、`hello world=591ms`。
- 影响：即使服务未退出，用户也会经历 1–7s 级搜索卡顿。
- 根因判断：compaction 构建/交换阶段与 query 的 shared data、page residency、锁范围或 CPU/I/O 资源竞争没有充分隔离。

### High：25% 阈值触发太晚

- 证据：前几轮在 24.48% 已出现多路径秒级慢点；本轮到 25.0006% 才 full compaction。
- 影响：系统在触发 compaction 前已经积累了 180万+ tombstones 和大量 flush/rewrite 长尾。
- 根因判断：固定 25% 作为 runtime 触发点不适合交互式搜索场景。

### High：compaction 全流程耗时约 20 分钟

- 证据：16:37:27 触发，16:57:52 done。
- 影响：长时间后台维护窗口增加与查询、flush、HTTP 服务冲突的概率。
- 根因判断：full compaction 一次处理 7.3M records，粒度过大，缺少分批或渐进式治理。

### High：日志缺少服务退出/HTTP server 生命周期证据

- 证据：`WARN=0 ERROR=0`，但 HTTP connection refused 且进程不在运行列表。
- 影响：无法从主日志判断是 crash、正常退出、HTTP server 停止、还是外部因素终止。
- 根因判断：可观测性不足，尤其在 compaction 这种高风险维护路径上缺少 fatal/exit/server-stop 日志。

### Medium：flush 长尾与 compaction 叠加

- 证据：`FLUSH_GE5=243`、`FLUSH_GE10=43`，compaction 前后多次 15–32s rewrite。
- 影响：写入维护任务可能共同扰动 mmap/page cache，并放大 query 退化。
- 根因判断：flush/rewrite/compaction 之间缺少全局资源调度与 backpressure。

## 9. 优化建议

### P0：先修服务可用性与进程生命周期观测

在优化查询路径之前，必须先回答“服务为什么拒绝连接”：

1. 在 HTTP server start/stop、App terminate、ServiceEngine 析构、uncaught exception、signal handler 处记录日志。
2. 若有 macOS crash report，应将崩溃摘要与主日志关联。
3. 在 compaction 开始、Phase 2、Phase 3、done 周围记录当前线程、锁等待、HTTP server 状态。
4. 对 `/api/status` 增加轻量健康检查，不应被 compaction 长时间阻塞。

验收标准：下一次 connection refused 能明确归因到 crash、正常退出、server stop 或端口绑定失败，而不是只能从外部观察推断。

### P0：compaction 必须与在线查询隔离

建议将 COW compaction 改成真正的后台构建 + 短锁交换：

- Phase 2 构建 compacted data 时不阻塞 query 读取旧 snapshot；
- Phase 3 pointer swap 必须是毫秒级短锁；
- replay adds/deletes 不应阻塞 HTTP server 接受连接；
- compaction 期间 `/api/status` 和短查询必须保持可用。

验收标准：full compaction 期间 `.pdf`、`*.swift`、`main.cpp` 不超过正常冷态阈值，HTTP status 不 timeout、不 connection refused。

### P0：将固定 25% 阈值前移或改为 debt-based compaction

本轮证明 25% 会触发，但触发太晚。建议：

- 将强制 full compaction 阈值前移到 8–10%；
- 或以 debt score 触发：tombstone ratio、tombstone 绝对数量、full-scan p95、flush GE10、skipflush 增量共同计算；
- 使用小批量 incremental reclaim，避免一次性处理 7.3M records。

验收标准：tombstone ratio 不再接近 25%，且不再出现 20 分钟级 full compaction 窗口。

### P1：给 compaction 增加限速与资源隔离

- 限制 compaction CPU 并发，避免抢占查询线程。
- 对磁盘 rewrite 做 I/O throttling。
- 在 compaction 运行时暂停或合并普通 flush，避免 flush rewrite 与 compaction 同时争抢 page cache。
- 对 query 线程设置优先级或让查询使用旧 snapshot 热页。

验收标准：compaction 期间 `FLUSH_GE10` 不继续快速增加，query tail latency 不出现秒级尖峰。

### P1：修正 report parser 指标命名

当前日志已经有 COW compaction，但 `RECLAIM=0` 容易误导。建议后续 parser 拆分：

- `COMPACTION_TRIGGER`
- `COMPACTION_PHASE2`
- `COMPACTION_SWAP`
- `COMPACTION_DONE`
- `RECLAIM` 若仅表示某种旧路径，应明确命名。

这样后续报告可以避免“RECLAIM=0 但 compaction 已执行”的语义冲突。

### P2：保留固定 query battery，但增加 compaction-aware probe

建议下一轮若服务恢复：

- 在 compaction 期间每 5s 请求 `/api/status` 和 `q=x`；
- 单独记录 connection timeout 与 refused；
- 对 `.pdf`、`*.swift`、`main.cpp` 增加 compaction 窗口内重复 probe；
- 将 compaction 状态加入 status 返回，方便外部脚本判断。

## 10. 下一轮重点

1. 重启 MacEverything 后确认服务是否恢复。
2. 检查是否存在 macOS crash report 或应用退出记录。
3. 再跑一次 status，记录 compaction 后 `recordCount/liveRecordCount/tombstoneRatio` 是否已降至健康区间。
4. 若 tombstone 已降低，比较 full-scan floor 是否改善。
5. 若服务再次在 compaction 或 flush 压力下退出，优先修可用性而非局部查询优化。

## 11. 结论

本轮完成了前序多轮最关键的验证：25% tombstone 阈值确实触发 full COW compaction，并将 7,329,723 records compact 到 5,497,248 records。但触发方式暴露了更严重问题：compaction 期间查询出现 1–7s 级尾延迟，后续 probe 全部 timeout，最终 HTTP 服务 connection refused 且进程不在运行列表。

因此当前最高优先级不是继续证明 tombstone 会导致慢查询，而是确保 compaction 能在服务在线时安全、平滑、可观测地执行。建议优先修复服务可用性观测、compaction/query 隔离和前移式 debt-based reclaim。
