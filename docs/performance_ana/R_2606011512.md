## 7. 问题清单

### High：接近 25% tombstone 阈值但仍未触发 reclaim

- 证据：`FINALSTATUS|7276442|5494814|1781628|24.48`，`RECLAIM=0`。
- 影响：full-scan 路径需要扫描 7.27M 槽位，而有效 live 数据只有 5.49M；约 178万 tombstone 持续增加无效扫描面。
- 风险：一旦继续增长并越过 25%，如果 reclaim 仍不触发，查询地板会继续抬升；如果触发时机太晚，reclaim 本身可能造成更大写入/页面扰动。
- 根因判断：当前 reclaim 策略过晚或触发条件过严，无法在读路径出现明显退化前降低扫描债务。

### High：full-scan / string-scan 路径发生可复现秒级慢查询

- 证据：`中文测试` 最高 3390ms，`path:/Users` 最高 1667ms，`content:import` 最高 1537ms，`size:>100m` 最高 1536ms。
- 影响：用户输入中文、path 或 content 查询时可能出现 1–3s 卡顿，且慢点发生在锁内 phase2，可能拖累并发查询。
- 根因判断：这些路径共同特点是候选剪枝弱或为 0、需要扫描大列/大槽位；在高 tombstone 与页面驻留不稳时，成本被放大。

### High：锁内 phase2 与总耗时高度一致

- 证据：battery 中 `path:/Users` 为 `totalMs=571.33`、`phase2Ms=563.30`、`lockHeldMs=563.30`；`content:import` 为 `totalMs=442.34`、`phase2Ms=436.23`、`lockHeldMs=436.23`；`中文测试` 为 `totalMs=353.82`、`phase2Ms=351.87`、`lockHeldMs=352.63`。
- 影响：慢查询不只是单个请求慢，还会延长共享锁或关键区占用，增加尾延迟扩散风险。
- 根因判断：查询执行与共享数据访问耦合过紧，full-scan 工作仍在锁保护范围内完成。

### Medium：flush 长尾继续增加，并与慢查询时间窗重叠

- 证据：`FLUSH_GE5=200`、`FLUSH_GE10=33`，本轮新增多个 12–19s flush。
- 影响：写入路径长尾可能扰动 page cache / mmap residency，并与读路径竞争 I/O 或内存带宽。
- 根因判断：flush/rewrite 批次大小、频率或调度与查询路径缺少隔离。

### Medium：trigram 高频候选查询仍有 phase2 成本

- 证据：`test` candidates=149,913，reprobe 出现 303.32ms、458.05ms；`abc def ghi jkl mno pqr` 首轮 368.47ms。
- 影响：高频词或多词查询虽然通常可回暖，但首轮/冷态仍会造成明显延迟。
- 根因判断：候选集合较大时，phase2 验证成本仍可能退化为大量记录访问。

## 8. 优化建议

### P0：把 runtime reclaim 从“接近 25% 才处理”提前到 8–10% 或 debt-based 触发

当前 24.48% tombstone 已经伴随秒级慢查询，说明 25% 阈值对交互式搜索太晚。建议改为：

- tombstone ratio 达到 8–10% 时触发后台 reclaim；或
- 使用 debt-based 策略：结合 `tombstones` 绝对数量、full-scan 查询延迟、flush 长尾和 rewrite 密度动态触发；
- reclaim 需要分批、限速，避免一次性大 rewrite 造成更严重页面扰动。

验收标准：在 tombstone ratio 低于 10–12% 的稳定状态下，`content/path/中文` full-scan floor 不再频繁超过 500ms。

### P0：为 full-scan 路径增加页触碰/列访问观测

现有日志能证明 `phase2≈lockHeld≈total`，但还不能区分：

- 哪些列被访问最多；
- 是否发生 page fault；
- 是否因为字符串解码、lowercase pool、path pool 或 content metadata 导致额外页面触碰；
- GCD 分片是否负载不均。

建议在 `advanced-linear-gcd` 和 `advanced-pure-filter-soa-gcd` 增加轻量统计：

- scanned slots / live slots / tombstone skipped；
- 每列触碰计数；
- 每 chunk elapsed p50/p95/max；
- phase2 内部按 filter/path/string/content 分段计时。

验收标准：下一轮报告可以把 `中文测试` 与 `path:/Users` 的 1–3s 慢点拆成明确的列访问或 chunk 长尾，而不是只看到 phase2 总耗时。

### P1：将 full-scan 读路径从写入/flush 扰动中隔离

建议评估 immutable snapshot / pointer-swap publication：

- 查询线程读取稳定快照；
- 写入线程构建新结构后原子发布；
- flush/rewrite 不直接影响当前查询使用的热页集合。

验收标准：长 flush 出现时，`path:/Users`、`content:import`、`中文测试` 不再同步出现秒级慢查询簇。

### P1：为 content/path/中文路径增加 targeted prewarm

在 rewrite/compaction/large flush 后，对最容易退化的列做小规模预热：

- path lower pool / path index pages；
- content metadata pages；
- string normalization / unicode scan 需要触碰的列；
- pure-filter 数值列。

预热必须限速，避免用大量内存换性能；目标是减少首次查询 page fault，而不是常驻复制整份索引。

验收标准：rewrite/flush 后首轮 `content/path/中文` 不再出现 1s+ 冷启动尖峰。

### P2：为高频 trigram 候选增加 phase2 限流或更细剪枝

`test`、`abc def ghi jkl mno pqr` 的候选验证仍可出现 300–450ms 冷点。建议：

- 对高频 token 增加候选上限或更细的 early rejection；
- 对多词 query 使用更稳定的 token 选择策略，优先使用低频 token 缩小候选；
- 对空结果长 query 更早退出，避免无意义 phase2。

验收标准：`test` 和多词长 query 的冷态 reprobe 不超过 200ms，热态稳定在几十毫秒内。

## 9. 下一轮重点验证

1. 继续观察 tombstone ratio 是否越过 25%。
2. 如果越过 25%，必须确认 `RECLAIM` 是否从 0 增加。
3. 若 `RECLAIM` 仍为 0，说明 reclaim 阀门条件与实际运行状态不一致，应优先审查触发逻辑。
4. 若 `RECLAIM` 增加，需要观察是否伴随更大的 flush/rewrite 和查询慢点，避免“回收本身制造尾延迟”。
5. 对 `中文测试`、`path:/Users`、`content:import` 保持每轮 floor/reprobe，它们是当前最敏感的退化探针。

## 10. 结论

本轮是最近几轮中信号最强的一轮：固定 query battery 直接触发新增慢查询簇，`QUERYADV_GE500` 从 90 增至 114，`FLUSH_GE5` 从 184 增至 200，`FLUSH_GE10` 从 27 增至 33，tombstone ratio 达到 24.48%，但 `RECLAIM=0`。

当前首要问题不是某一个 query 写得慢，而是索引 tombstone 债务、full-scan 锁内执行、页面驻留扰动和 flush/rewrite 长尾叠加。优先级最高的治理方向是提前并平滑 reclaim，同时补齐 full-scan 内部观测，让下一步优化能够定位到具体列、chunk 或页面访问模式。
