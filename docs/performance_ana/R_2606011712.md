## 6. 问题清单

### Critical：服务持续不可用，所有 HTTP 请求 connection refused

- 证据：16 个 battery query、status、floor/reprobe、final status 全部 connection refused；进程检查没有 MacEverything。
- 影响：搜索服务完全不可用，用户无法执行任何查询。
- 根因判断：与上一轮 25% full compaction 后的 timeout/refused 状态连续，但现有日志没有进程退出原因。
- 优先级：最高。

### Critical：compaction 完成后没有服务恢复证据

- 证据：最新日志停在 `COW compaction done`，之后没有 HTTP server restart、ServiceEngine ready、Log session started 或错误日志。
- 影响：即使 compaction 自身完成，服务层仍没有恢复到可用状态。
- 根因判断：compaction 生命周期与应用/HTTP server 生命周期之间缺少恢复保障或可观测性。

### High：日志没有记录退出/HTTP server 停止原因

- 证据：`WARN=0 ERROR=0`，但服务外部不可达且进程不存在。
- 影响：无法从主日志判断是 crash、正常退出、server stop、端口释放还是外部 kill。
- 根因判断：关键生命周期日志缺失，尤其缺少 fatal signal、uncaught exception、applicationWillTerminate、HTTP server stop、ServiceEngine destructor 等记录。

### High：25% full compaction 对在线服务的安全性不足

- 证据：上一轮 compaction 窗口内出现秒级查询、后续 timeout；本轮服务仍 connection refused。
- 影响：compaction 不是透明后台维护，会演变为服务级故障。
- 根因判断：full compaction 的资源占用、锁/快照交换、HTTP server 可用性没有被统一保护。

### Medium：parser 指标仍存在语义冲突

- 证据：日志明确有 COW compaction，但汇总仍显示 `RECLAIM=0`。
- 影响：报告读者可能误以为没有回收动作。
- 根因判断：`RECLAIM` 计数与 COW compaction 不是同一语义，需要拆分指标。

## 7. 优化建议

### P0：先补服务生命周期与崩溃观测

必须先让下一次故障能被明确归因：

1. 在 app 启动、HTTP server start/stop、ServiceEngine start/stop、application terminate 处写日志。
2. 增加 uncaught exception、signal handler、fatal error 日志。
3. 若 macOS crash report 存在，应在报告或日志中关联 crash UUID / timestamp。
4. 在 compaction done 后记录 HTTP server 是否仍监听 `19860`。

验收标准：再次出现 connection refused 时，日志能明确说明进程退出、server 停止或端口绑定状态。

### P0：compaction 后必须保持或恢复 HTTP 服务

即使 compaction 需要长时间执行，HTTP 层也应保持健康：

- `/api/status` 不应依赖重扫描或长锁；
- compaction done 后应显式验证 SearchEngine snapshot 与 HTTP handler 仍可用；
- 如果 compaction 失败，应回滚到旧 snapshot，而不是影响 server 生命周期；
- 如果进程即将退出，应记录原因。

验收标准：full compaction 后 `curl http://localhost:19860/api/status` 可持续返回，并且 query battery 可继续执行。

### P0：将 full compaction 改为可中断、可限速、可恢复

当前一次性处理 7.3M records 的 compaction 风险过高。建议：

- 分批 compact，而不是一次性 full compaction；
- 对 CPU/I/O 做限速；
- 在每个阶段检查 cancellation/health；
- 保留旧 snapshot，直到新 snapshot 完整发布且 HTTP health check 通过；
- compaction 失败时自动降级或延迟重试。

### P1：前移 compaction 触发，避免 25% 临界大维护

前序证据显示 24.48% 已经出现慢查询，25% 才 full compaction 太晚。建议改为：

- 8–10% tombstone ratio 开始渐进 reclaim；
- debt score 结合 tombstone 数量、flush GE10、full-scan p95 和 skipflush；
- 避免积累到 180万+ tombstones 后才做大规模维护。

### P1：拆分日志 parser 的 compaction/reclaim 指标

建议后续报告脚本拆分：

- `COMPACTION_TRIGGER`
- `COMPACTION_PHASE2`
- `COMPACTION_SWAP`
- `COMPACTION_DONE`
- `RECLAIM_LEGACY` 或移除 `RECLAIM` 模糊项

这样能避免“compaction 已执行但 RECLAIM=0”的误导。

## 8. 下一轮重点

1. 先启动或恢复 MacEverything，再确认 `http://localhost:19860/api/status` 是否可用。
2. 检查 macOS crash report、Console log 或 app lifecycle log，定位进程为何不存在。
3. 若服务恢复，读取 status，确认 compaction 后 `recordCount/liveRecordCount/tombstoneRatio` 是否已回落。
4. 再运行固定 query battery，比较 compaction 后 full-scan floor 是否改善。
5. 如果服务再次在 compaction 后不可用，应停止常规性能优化，优先修服务生命周期与 compaction recovery。

## 9. 结论

本轮不是性能数值对比，而是服务可用性复核：所有 query 与 status 请求均 connection refused，进程检查也没有 MacEverything。日志没有新增查询或错误，最新事件仍是上一轮 25% tombstone full COW compaction 完成。

因此，当前最紧急问题是 compaction 后服务没有保持或恢复可用。下一步应优先补齐服务生命周期观测、崩溃/退出诊断和 compaction recovery 机制，然后再回到 query 延迟优化。
