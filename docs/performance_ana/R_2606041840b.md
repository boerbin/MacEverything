### Flush I/O 风暴——本轮灾难的根因

| 指标 | 值 | 说明 |
|------|---:|------|
| 新会话总 flush 次数 | 52 | 82 分钟内 |
| flush 频率 | ~1.6 分钟/次 | 极高 |
| 单次 rewrite 时间 | 11-18 秒 | 写入 ~2.2GB |
| flush 占用磁盘时间估算 | ~700-900 秒 | **82 分钟中 12-15 分钟在 flush** |
| flush 期间磁盘利用率 | ~100% | 重写整个文件 |

- **flush 重写导致三重灾难**：
  1. **I/O 带宽饱和**——phase2 顺序扫描被阻塞（50-2,773 倍退化）
  2. **lockWait**——flush 持锁 11-18 秒阻塞查询（最高 620ms）
  3. **tombstone 制造**——flush 每次重写产生大量中间状态 tombstone

- **R107 为什么正常**？——R107 查询恰好在两次 flush 之间执行（flush 间隔 ~1.6 分钟，查询电池 ~30 秒），磁盘空闲。本轮查询与 flush 重写时间窗口重叠。

- **FLUSH=52**——每次重写整个 flat index 文件（~2.2GB），保留所有 tombstone。

## 6. 问题清单

### Critical：Flush I/O 风暴——15/16 >500ms 的根因

- **52 次 flush 在 82 分钟内，每次重写 ~2.2GB——累计写入 ~114GB。**
- **磁盘 I/O 带宽被 flush 完全占据**——phase2 退化 50-2,773 倍。
- **flush 持锁 11-18 秒**——lockWait 最高 620ms。
- **flush 不清理 tombstone**——纯粹的 WAL 持久化，但产生了灾难级 I/O 负载。
- **R107 的"恢复"是 flush 间隙的侥幸**——当查询与 flush 时间窗口重叠时即发生灾难。

## 7. 优化建议

### P0 紧急：降低 Flush 频率——当前 flush 是性能灾难的根因

- **问题**：flush 每 ~1.6 分钟触发一次，每次重写 2.2GB 文件耗时 11-18 秒——82 分钟内累计写入 ~114GB。
- **方案 A**：提高 flush 触发阈值——从 100 条 pending changes 提高到 10,000 条，或增加最小间隔（如 5 分钟）。
- **方案 B**：增量 flush——仅追加新记录到文件末尾，避免每次全量重写。
- **预期收益**：消除 I/O 饱和，phase2 恢复正常，lockWait 消除。

### P0 紧急：Flush 重写时跳过 tombstone（合并 flush 与 compaction）

- **当前 flush 重写整个文件但保留 tombstone**——既承受了全量重写的 I/O 成本，又没有获得 compaction 的收益。
- **方案**：flush 重写时检查 tombstoneRatio，超过 5% 时自动跳过 tombstone 记录——零额外 I/O 成本获得 compaction 效果。

### P0 紧急：Flush 期间降级锁策略

- **方案**：flush 重写使用 copy-on-write——写入临时文件后原子替换，flush 期间不持有写锁。
- **预期收益**：消除 flush 引起的 lockWait（当前最高 620ms）。
