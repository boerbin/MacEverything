## 9. 可能问题定位

### P0-1：runtime reclaim 阀门仍不可达，墓碑升至 22.52%
- 证据：R1112 末 tomb=1,591,836，ratio=22.52%；`RECLAIM=0`；阀门为 25%。
- 影响：扫描上限、mmap page footprint、full-scan working set 持续膨胀。
- 根因：25% 阈值对当前 22%+ 长期高压区间不敏感。

### P0-2：full-scan 仍在持锁窗口内完成
- 证据：`content` lockHeld=204.85ms / total=218.02ms；`path` lockHeld=146.24ms / total=154.97ms；`中文` lockHeld=219.02ms / total=219.05ms。
- 影响：page fault / cache miss / rewrite 干扰都会变成持锁尾延迟。
- 根因：读路径没有通过不可变快照与 flush/publish 解耦。

### P0-3：string/filter 页状态缓慢恢复但不稳定
- 证据：W2 floor 较 R1042 改善，但 `content` 再探 max=475.73ms，接近慢查询阈值。
- 影响：用户常见 path/content/中文查询仍可能出现百毫秒级或近 500ms 的尾部。
- 根因推断：大 rewrite 后页状态靠自然访问回暖，后续中等 rewrite 密度又会扰动 page cache。

### P1：flush 中等重写密度重新抬头
- 证据：R1042 后新增 4 次 5–6s rewrite，`FLUSH_GE5 121→125`，但 `FLUSH_GE10` 仍为 21。
- 影响：当前未造成新查询事故，但可能延缓 full-scan 平台清空。
- 根因：flush 调度与查询读路径共享 I/O/cache/锁资源。

## 10. 优化建议

1. **将 runtime reclaim 阀门从 25% 下调到 8–10%**  
   当前 22.52% 仍无法触发 reclaim，且 tombstone 继续单调上升。下调后用日志验证 reclaim 次数、rewrite 时长、full-scan floor 与 GE500 是否改善。

2. **读写解耦：查询读不可变快照，flush 通过指针交换发布**  
   本轮慢项继续满足 `lockHeld≈total`。根因修复应缩短锁内区域，让 page fault 与 full-scan 不再扩大为全局锁尾延迟。

3. **对 string/filter 热页做 rewrite 后预热或 `madvise(WILLNEED)`**  
   W2 floor 改善说明页状态可恢复，但恢复慢且会被 rewrite 扰动。预热应限于 path/name/content 相关 slot 页，不复制完整索引。

4. **flush storm guard 按密度触发**  
   本轮新增 4 次中等 ≥5s rewrite，虽未造成查询事故，但密度明显高于 R1042。guard 应按滚动窗口内 rewrite 总时长/次数触发，而不是只看单次是否超过 10s。

5. **补充 SKIPFLUSH 与 flush debt 语义日志**  
   `SKIPFLUSH=26` 未再涨，但仅靠计数无法判断债务是否缓解。建议记录 pending、阈值、skip reason、距上次成功 flush 的间隔。

6. **full-scan 分段预算与让出**  
   在无锁快照完成前，先给 path/content/中文 full-slot scan 加分段预算，降低单次不可中断窗口，避免 475ms 这类近阈值尾部继续放大。

**资源平衡说明**：以上建议优先调整阈值、锁边界、调度和 page hint，不引入大内存倒排表，也不要求额外重计算。预热以 OS hint 或小范围顺序触碰为主；无锁快照只允许 flush 发布期间的有界短暂版本窗口。
