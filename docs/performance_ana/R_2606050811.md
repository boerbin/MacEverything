## 6. 问题清单

### Medium：白天 I/O 竞争导致全面性能退化

- 3/16 >500ms，P50 从 30ms 升至 81ms（↑2.7x）。
- **根因**：白天其他进程（Finder、Spotlight、IDE、浏览器、编译器）竞争：
  - 物理内存 → page cache 被回收 → 全表扫描变慢。
  - CPU 调度 → 线程切换延迟增加 → 所有查询变慢。
  - 磁盘 I/O → flush rewrite 变慢 → lockWait 增加。
- **这是 OS 级行为，非 MacEverything 问题。**
- **自然缓解**：查询活动持续 → page cache 逐步预热。compaction 触发后记录数减少 → 全面改善。

### Medium：lockWait 回升（4/16, max 71ms）

- flush rewrite 3.6s + 白天调度延迟 → 锁持有窗口更易被命中。
- **71ms lockWait 对用户可感知但非严重**——大多数交互式搜索仍在 <200ms 完成。
- **compaction 后将自然改善**——记录数减少 → rewrite 更快 → lockWait 更少。

### 正面：`path:/Users` 实际改善（去除 lockWait）

- queryTime=611ms 中 lockWait=71ms → 纯搜索时间=540ms。
- R131 纯搜索时间=642ms → **实际 page cache 改善 16%**。
- **lockWait 使外观数据变差，但搜索引擎本身在改善。**

## 7. 优化建议

### P1：降低 Compaction 阈值至 15%（最关键建议）

- 当前 6.30%，白天平均增速 ~1,500/min 时约 4-6 小时达到 15%。
- **compaction 收益**：
  - 减少 ~15% 记录 → rewrite 时间缩短 ~15% → lockWait 降低。
  - 减少全表扫描数据量 → phase2 改善。
  - 释放内存 → page cache 改善。
- **这是唯一能在不改代码的情况下系统性改善性能的措施。**

### P2：观察 lockWait 趋势

- 如果 lockWait 持续 >100ms 或影响 >50% 查询，需考虑：
  - flush 间隔从 30s 调整为 45s（减少锁频率）。
  - 或将 rewrite 改为 shadow copy 方式（rewrite 期间不阻塞读）。
- **当前 71ms 尚可接受——继续观察。**

### 无其他建议

- 白天 I/O 竞争是 OS 行为，MacEverything 无法直接控制。
- compaction 是最有效的系统性优化——等待自然触发或手动降低阈值。

## 9. 结论

**3/16 >500ms（`path:/Users`=611ms, `中文测试`=604ms, `content:import`=477ms 边缘），lockWait 回升至 4/16(max 71ms)。** 白天 I/O 竞争全面展开——P50 从 30ms 升至 81ms（↑2.7x），即使 cache 命中查询也慢了 10 倍（系统调度延迟）。

**关键洞察**：去除 lockWait 后，`path:/Users` 纯搜索时间=540ms（R131=642ms，实际改善 16%）——**搜索引擎本身在持续改善，lockWait 是外部因素叠加。** flush rewrite 峰值 3.6s，tombstone 6.30%（387K），白天增速脉冲式波动（765-2,731/min）。

**P1 建议：降低 compaction 阈值至 15%**——预计 4-6 小时内自然触发（约 12:00-14:00），compaction 后记录数减少将系统性改善 rewrite 时间、lockWait 和全表扫描性能。当前退化完全由白天 I/O 竞争驱动——是正常的日夜周期表现，不代表系统缺陷。
