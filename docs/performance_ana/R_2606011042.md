## 9. 可能问题定位

### P0-1：runtime reclaim 阀门仍不可达，墓碑升至 22.40%
- 证据：R1042 末 tomb=1,581,335，ratio=22.40%；`RECLAIM=0`；已知阀门为 25%。
- 影响：扫描 working set 和 mmap page footprint 持续膨胀。
- 根因：按 25% 才触发的回收策略对 21–22% 长期高压区间不敏感。

### P0-2：full-scan 仍在持锁窗口内完成
- 证据：`path` lockHeld=260.94ms / total=267.43ms；`中文` lockHeld=244.59ms / total=244.62ms；`content` lockHeld=224.83ms / total=233.10ms。
- 影响：page fault、cache miss、顺序全扫都会直接变成持锁尾延迟。
- 根因：读路径没有通过不可变快照把 query scan 与 flush/publish 锁边界拆开。

### P0-3：string/filter 页状态仍未稳定恢复
- 证据：`path` 再探 floor=138.04ms、max=337.16ms；W2 floor=170.98ms；`content` W2 floor=177.46ms。
- 影响：用户常见路径/内容/中文搜索仍在百毫秒平台。
- 根因推断：大 rewrite 之后索引页被驱逐，自然 re-fault 回暖可发生，但被后续 flush 扰动反复打断。

### P1：flush 压力没有再次加速，但仍在推进
- 证据：`FLUSH 1114→1174`、`FLUSH_GE5 120→121`、`SKIPFLUSH=26` 不变；新增 10:32 rewrite=5919ms。
- 影响：本轮没有造成查询事故，但仍可能延缓平台清空。
- 根因：flush 调度与查询读路径共享 page/cache/锁资源。

## 10. 优化建议

1. **将 runtime reclaim 阀门从 25% 下调到 8–10%**  
   当前 22.40% 仍无法触发 reclaim，且 tombstone 单调上行。下调后应验证：reclaim 是否出现、rewrite 时长是否可控、全扫 floor 是否下降。

2. **读写解耦：查询读不可变快照，flush 通过指针交换发布**  
   本轮慢项继续满足 `lockHeld≈total`，这是根因级证据。目标是让 query scan 不持有 flush/publish 的重锁，切断 page fault 对全局锁的放大。

3. **string/filter 热页预热或 `madvise(WILLNEED)`**  
   再探 floor 缓慢下降但 W2 反弹，说明自然回暖不稳定。预热应聚焦 path/name/content 相关 slot 页，不复制完整索引，避免用大内存换延迟。

4. **flush storm guard 按密度触发**  
   本轮只有孤立 5.9s rewrite，没有新查询事故；历史事故来自密集簇。guard 应基于滚动窗口内 rewrite 次数/总时长，而不是单次中等 rewrite。

5. **补充 SKIPFLUSH 语义日志**  
   `SKIPFLUSH=26` 本轮未继续上涨，但仍无法判断每次 skip 是健康节流还是债务累积。建议记录 pending、阈值、skip reason、距上次成功 flush 的间隔。

6. **full-scan 分段预算与让出**  
   在无锁快照完成前，可先降低单次 full-slot scan 的不可中断窗口，限制 `path`/`中文`/`content` 的尾部抖动。

**资源平衡说明**：以上建议优先改阈值、锁边界、调度和 page hint，不引入大内存索引表，也不要求额外重计算。预热应以 OS hint 或小范围顺序触碰为主；无锁快照只允许 flush 发布期间的有界短暂版本窗口。
