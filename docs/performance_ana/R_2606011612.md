## 7. 问题清单

### High：tombstone ratio 已升至 24.85%，但 `RECLAIM=0`

- 证据：`FINALSTATUS|7313451|5496371|1817080|24.85`，日志 `RECLAIM=0`。
- 影响：约 181.7 万 tombstone 仍参与 full-scan 扫描面，且距离 25% 阈值仅约 0.15 个百分点。
- 根因判断：现有 reclaim 触发点晚于性能风险出现点，且到目前为止没有实际 reclaim 记录。
- 风险：下一轮一旦超过 25%，若 `RECLAIM` 仍不增加，说明阀门条件可能不符合运行实际；若突然大规模 reclaim，也可能带来新的 flush/rewrite 尾延迟。

### Medium：读路径回暖但 full-scan 成本仍高

- 证据：`content:import` 最高 320.89ms，`path:/Users` 最高 372.17ms，`中文测试` 最高 323.60ms。
- 影响：虽然没有慢查询日志，但交互式搜索仍可能出现 150–370ms 的可感知延迟。
- 根因判断：这些路径仍依赖大范围扫描和字符串/内容列访问，热态成本也无法与结构化索引路径相比。

### Medium：full-scan 仍持有锁接近完整查询耗时

- 证据：battery 中 `content:import` 的 `phase2Ms=149.87`、`lockHeldMs=149.87`；`path:/Users` 的 `phase2Ms=154.03`、`lockHeldMs=154.03`；`中文测试` 的 `phase2Ms=172.54`、`lockHeldMs=173.00`。
- 影响：单次查询当前不算极慢，但锁持有时间仍足以在并发或冷态下放大尾延迟。
- 根因判断：查询扫描与共享索引锁耦合过紧。

### Medium：flush 长尾继续积累，`SKIPFLUSH` 增至 28

- 证据：`FLUSH_GE5=228`、`FLUSH_GE10=38`、`SKIPFLUSH=28`。
- 影响：后台写入/flush 压力仍可能在下一轮扰动 page cache，重新触发 content/path/中文慢点。
- 根因判断：flush/rewrite 与查询热页之间缺少足够隔离，且维护任务可能被门控跳过。

### Low：trigram 路径当前健康但仍需保持观察

- 证据：`test` candidates=149,959 但 totalMs=15.81；`.pdf=14.04`；`README=11.24`。
- 影响：本轮不是主要风险。
- 根因判断：trigram postings 当前处于热态，候选验证成本可控。

## 8. 优化建议

### P0：下一轮必须验证 25% reclaim 行为

当前距离 25% 已很近，下一轮应把 `FINALSTATUS` 与日志 `RECLAIM` 作为第一判断项：

- 如果 tombstone ratio > 25% 且 `RECLAIM=0`，优先审查 reclaim 触发条件；
- 如果 `RECLAIM>0`，观察是否伴随 `FLUSH_GE10` 或新的慢查询簇；
- 如果 ratio 被压回 25% 以下，记录 reclaim 后的 full-scan floor 是否改善。

### P0：将 reclaim 从固定阈值改为 debt-based 或前移阈值

24.48% 时已出现秒级慢点，说明固定 25% 阈值过晚。建议：

- 将 runtime reclaim 触发目标前移到 8–10%；
- 或基于 tombstone 数量、full-scan p95、flush 长尾和 SKIPFLUSH 计数综合触发；
- reclaim 必须分批、限速、后台化，避免一次性 rewrite 抖动。

### P1：缩短 full-scan 锁范围

`phase2Ms≈lockHeldMs` 的证据跨多轮持续存在。建议：

- 引入 immutable snapshot / pointer-swap publication；
- 或至少将 full-scan 的长循环移出全局锁，只在获取快照指针和元数据边界时持锁；
- 对 path/content/中文路径优先试点。

### P1：给 path/content/中文路径增加针对性索引或预热

虽然本轮回暖，但这三类路径仍是最重路径。建议：

- path 查询增加 segment/token 索引，减少全槽字符串扫描；
- content 查询增加 opt-in metadata 索引或更窄的候选剪枝；
- 中文 query 增加 normalization/cache 或专门的 substring 索引策略；
- rewrite/large flush 后对相关列做限速 prewarm。

### P2：补齐维护任务观测

`SKIPFLUSH` 增加但日志只给出计数，建议记录：

- skip 原因；
- pending entries；
- flush/rewrite batch size；
- reclaim eligible bytes/slots；
- 当前 tombstone threshold 判定值。

这样可以直接判断为什么 `RECLAIM=0`。

## 9. 下一轮重点

1. 重点观察 tombstone ratio 是否越过 25%。
2. 若越过 25%，立即确认 `RECLAIM` 是否增加。
3. 继续对 `content:import`、`path:/Users`、`中文测试` 做 floor/reprobe。
4. 关注 `SKIPFLUSH` 是否继续增长。
5. 如果出现 reclaim，比较 reclaim 前后 full-scan floor 和 flush 长尾变化。

## 10. 结论

本轮性能表面上是好消息：没有新增慢查询，固定 query battery 也没有 ≥500ms 样本，trigram 和 full-scan 路径都明显回暖。但底层风险继续累积：tombstone ratio 已达 24.85%，`RECLAIM=0`，`SKIPFLUSH` 增至 28，flush 长尾继续增加。

因此，本轮应被视为“临界阈值前的热态恢复”，而不是问题解决。下一步的关键不再是证明查询会慢，而是验证接近 25% 的 reclaim 阀门是否真实有效、是否足够平滑，以及它能否降低 full-scan 扫描债务而不制造新的尾延迟。
