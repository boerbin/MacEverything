## 10. P0 优化建议

1. **立即下调 `:159` 比率阀 0.25→8–10%**：墓碑已到 19.07%，连续 21 轮运行期 compaction=0；继续等 25% 会让 rewrite 成本继续上升。
2. **storm guard 应以 flush 事件触发，而不是以慢查询触发**：本轮 19:42 已有 10.1s rewrite，但查询刚好未跨 500ms；若等慢查询出现才保护，就会重复 R128 的 2.56s dm 事故。
3. **读写解耦 / lock-free snapshot flush**：R128 证明同一查询组可在污染窗内被推到秒级，本轮证明同一系统也会短暂退潮；根因是读路径仍受 flush/页态相位调制。
4. **dm 列 mlock/madvise 仍优先**：本轮 dm 没有秒级化，但 floor 51ms、再探最高 116ms，仍是数值层最脆弱锚点。
5. **查询超时/熔断保持 P0**：R129 没有新增慢查询只是采样运气；R128 的 `dm:today` 2558ms 已经是常用查询的用户可见故障。

## 11. 结论

- **定性**：🟠 查询侧暂时稳定，但底层风暴仍在；19:42 新增 10.1s rewrite，墓碑跨过 19%。
- **分裂**：clean/stable 口径 **55/55** 维持；对抗口径 1.29×，较 R128 污染窗恢复但仍窄。
- **关键发现**：
  - 电池、W1/W2、再探均无新增 ≥500ms 查询。
  - 电池 trigram 103–170ms 经再探回到毫秒级，不是永久退化。
  - flush ≥5s 65→67，≥10s 12→13，新增 19:42 10.1s rewrite。
  - 墓碑 1.285M/19.07%，运行期 compaction 仍为 0。
- **根因判断**：不可回收墓碑继续扩大 rewrite/扫描边界；查询是否慢主要取决于是否命中 flush 余震相位。本轮是避开强污染窗，不是结构恢复。
- **行动建议**：立即做比率阀 reclaim + storm guard；随后推进 lock-free snapshot flush 与 dm 列驻留，避免下一次 10s rewrite 再污染用户查询。
