## 6. 问题清单

### High：flush rewrite 持续 4-10 秒导致 lockWait 443ms

- 事件风暴使 flush 数据量增大 → rewrite 时间从 ~2.5s 升至 4-10s。
- lockWait 443ms——用户可明显感知到搜索延迟。
- **P0 建议（COW flush）仍然是最根本的解决方案。**

### Medium：tombstone 12.43%——接近 15% compaction

- 按当前风暴增速可能 14 分钟内触发 15% compaction。
- **compaction 将大幅改善**：
  - recordCount 从 6.59M 降至 ~5.77M → rewrite 数据量减少 12% → 时间缩短。
  - 全表扫描数据量减少 → phase2 改善。
  - 磁盘空间释放。
- **compaction 本身需要数分钟——期间可能引发查询延迟（类似 R134）。**

### 正面：搜索引擎本身性能良好

- 去除 flush 影响后 14/16 查询 <350ms。
- page cache 预热状态好——path:/Users=160ms（R133=56ms 是极限，当前 160ms 在正常范围）。
- trigram 引擎 P50=34ms——核心搜索引擎无退化。

## 7. 优化建议

### P0：flush rewrite 改为 COW 方式（优先级最高，不变）

- R134 的 70 秒和本轮的 10 秒 flush 都证明了这个问题的严重性。
- **COW 方案消除 rewrite 期间的锁阻塞——查询完全不受 flush 影响。**

### P1：降低 Compaction 阈值至 15%（即将自然触发）

- 当前 12.43%——可能在 14-50 分钟内自然触发。
- **compaction 后 recordCount 从 6.59M 降至 ~5.77M → flush rewrite 加速 ~12%。**
- **考虑进一步降低至 10%——减少事件风暴期的退化窗口。**

### P2：事件风暴期 flush 频率调整

- 白天风暴期每次 flush 的增量记录数更大 → rewrite 更慢。
- 考虑在事件流 >5,000/min 时自动延长 flush 间隔（如 60s）——减少锁频率。
- **这是 COW 的替代方案——COW 更根本，但 flush 频率调整更简单。**

## 9. 结论

**2/16 >500ms（flush 锁阻塞导致），tombstone 飙升至 12.43%（819K）——34 分钟内增加 355K 条（增速 10,449/min）。** 事件风暴使 flush rewrite 持续 4-10 秒，lockWait 最高 443ms。但去除 flush 影响后搜索引擎本身性能良好（14/16 <350ms，P50=34ms）。

**15% compaction 阈值迫近——按当前增速约 14-50 分钟内触发。** compaction 将减少 recordCount ~12% → flush rewrite 加速 → lockWait 降低。这是自然的自愈机制。

**P0 建议不变：flush rewrite 改为 COW 方式。** R134（70s 阻塞 46s）和 R135（10s rewrite, 443ms lockWait）连续两轮证明 flush 锁架构是目前系统最大的可用性风险。COW 从根本上消除 rewrite 期间的查询阻塞。
