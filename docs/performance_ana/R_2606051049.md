## 7. 优化建议

### P0：flush rewrite 改为 COW 方式（优先级最高，不变）

- R134（70s 阻塞 46s）、R135（10s rewrite, 443ms lockWait）、R136（5.4s rewrite, 101ms lockWait）连续三轮证明 flush 锁是系统最大的可用性风险。
- **COW 方案消除 rewrite 期间的锁阻塞——查询完全不受 flush 影响。**
- **即使 flush rewrite 正在恢复，COW 仍然必要——因为下一次 I/O 风暴随时可能再次触发长时间 rewrite。**

### P1：观察 15% compaction 触发后的效果

- 15% compaction 即将自然触发——这是最重要的观察点。
- **compaction 后预期**：
  - recordCount 从 6.62M 降至 ~5.77M（-13%）。
  - flush rewrite 时间缩短 ~13%（数据量减少）。
  - 全表扫描 phase2 改善。
- **compaction 本身可能持续数分钟——期间查询可能受影响。**

### P2：考虑降低 compaction 阈值至 10%

- 当前 15% 阈值导致事件风暴期间 tombstone 大量堆积（R135 达到 12.4%），延长了 flush rewrite 偏高的窗口。
- **10% 阈值可在事件风暴早期即触发 compaction——缩短退化窗口。**

## 8. 下一轮重点

1. **15% compaction 是否已触发**——这是本系列最重要的观察点。
2. compaction 期间和之后的查询性能。
3. compaction 后 flush rewrite 时间是否降至 <2.5s。
4. tombstone 增速变化——风暴是否已完全消退。

## 9. 结论

**1/16 >500ms（`.pdf`=561ms lockWait=101ms），tombstone 12.81%（847K）——事件风暴减速至 5,578/min（R135=10,449/min，↓47%）。** flush rewrite 从 R135 的 4-10s 回落至 2.7-5.4s，lockWait max 从 443ms 降至 101ms。`x` 从 523ms 恢复至 34ms——flush 阻塞解除。

**15% compaction 即将触发（~26-48 分钟内）。** compaction 将减少 recordCount ~13% → flush rewrite 加速 → lockWait 降低 → 全表扫描改善。这是系统自然的自愈机制。

**P0 建议不变：flush rewrite 改为 COW 方式。** 尽管当前 flush rewrite 正在恢复，但 R134-R136 连续三轮证明 flush 锁架构在 I/O 竞争场景下的脆弱性。COW 从根本上消除 rewrite 期间的查询阻塞，使系统在任何 I/O 条件下都能保持一致的查询响应时间。
