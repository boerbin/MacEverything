## 6. 问题清单

### P0：前台查询重新出现 >500ms 超标

- 证据：`.pdf`=1115.0ms，`main.cpp`=742.8ms；最新日志段 `QUERYADV_GE500` 从 12 增至 14。
- 影响：用户可直接感知到秒级等待，且本轮慢查询来自 trigram 路径，不再局限于 full-scan/linear-gcd。
- 判断：这是本轮最高优先级问题，需要把 foreground tail latency 与后台 flush/page-cache 状态关联起来。

### P0：lockWait 明显放大

- 证据：`.pdf` lockWait=171.7ms，`*.swift` lockWait=157.1ms。
- 影响：前台查询被后台写入/flush/update 阻塞超过 150ms，是可感知延迟的一部分。
- 判断：需要定位持锁阶段；当前 flush 刚发生 10.46s 完整重写，二者时序高度可疑。

### P0：最新常规 flush 升至 10.46 秒

- 证据：最新 flush total=10460ms，较上一轮 3340ms 上升 213%；`FLUSH=730`，较上一轮 +12；`SKIPFLUSH=0`。
- 影响：完整重写不仅耗时高，还可能冲刷搜索热数据 page cache，并与前台查询争抢 I/O/锁。

### P0：tombstone 在 13% 以上继续快速上行

- 证据：tombstone=836,173（13.63%），较上一轮增加 14,492。
- 影响：无效记录比例升高会放大扫描、过滤、索引重写和 compaction 成本。
- 判断：compaction/清理策略明显滞后，且已开始和 flush/query 尾部叠加。

### P0：trigram 路径也出现严重退化

- 证据：`.pdf` phase2=713.0ms，`main.cpp` queryTime=742.8ms；`hello world`=281.9ms，`*.swift`=206.2ms，`ext:cpp`=153.9ms。
- 影响：原本健康的 indexed/trigram 查询被推入高延迟区，说明问题不只是 full-scan。

### P1：非 phase2 成本缺少拆分

- 证据：`main.cpp` queryTimeMs=742.8ms 但 phase2Ms=76.5ms、lockWait=0ms；`x` queryTimeMs=67.6ms 但 phase2Ms=0；`MacEverything` queryTimeMs=71.1ms 但 phase2Ms=1.5ms。
- 影响：现有 timing 无法解释大量 top-level 延迟，难以定位是否为结果组装、路径加载、队列等待、HTTP 写出或 page-cache 缺页。

## 7. 优化建议

### P0：立即给 flush 加前台保护和退避

- 当前 latest flush 已达 10.46s，且本轮同时出现 171.7ms lockWait 与 2 个 >500ms 查询。
- 当最近 flush 超过阈值时，应提高下一次 flush 间隔、降低 batch 频率，或前台查询活跃时推迟大 flush。
- 持久化线程使用低 QoS，并评估大顺序写的 `F_NOCACHE`/同类策略，减少对搜索热页的冲刷。
- 验收：常规 flush 不再与 query battery 同期制造 >500ms 查询；lockWait 不再出现 100ms+。

### P0：flush 改为增量/COW 页写入

- 将 stable segment 与 delta segment 分离，常规 flush 只追加或替换小段 delta。
- 大段合并放到后台低优先级任务，不与前台查询争抢热页或持锁窗口。
- 验收：常规 flush total <200ms，latest session 不再出现分钟级 rewrite outlier。

### P0：立即提前或分段 compaction

- 不等待更高的全局 tombstone 阈值；结合绝对 tombstone 数、segment tombstone 率和 flush rewrite 成本触发局部 compaction。
- 优先处理 tombstone 密集 segment，避免 scan/filter 路径继续扫描大量无效记录。
- 验收：tombstone 率从 13%+ 回落，扫描/过滤路径稳定 <200-300ms。

### P0：拆分 top-level query timing

- 对所有路径增加 queueWait、lockWait、phase2、candidate materialization、path/file metadata load、sort/rank、result assembly、HTTP serialization/write 等阶段耗时。
- 对 `main.cpp` 这类 phase2 低但 top-level 高的案例，必须能解释差值来源。
- 验收：`queryTimeMs - phase2Ms - lockWaitMs` 不再是不可解释的大黑盒。

### P0：细分 trigram/postings 路径

- 对 `advanced-trigram` 记录 postings 读取、候选交并、候选评分、路径加载、结果组装、page-cache miss 近似指标。
- 对 `.pdf` 这类 candidates≈9860 但 phase2=713ms 的查询，定位是 postings 读取慢、候选处理慢还是结果加载慢。
- 验收：trigram 路径在 flush 后仍稳定 <100ms，或至少能解释冷启动成本。

### P1：为 advanced-linear-gcd 与 pure-filter 增加剪枝

- 对路径、中文、content/filter 类查询记录扫描记录数、tombstone 跳过数和 segment 分布。
- 评估路径分段索引、轻量字符 n-gram、预过滤位图或 segment-level skip list。
- 验收：`path:/Users`、`中文测试`、`content:import` 不再在 250-500ms 区间波动。
