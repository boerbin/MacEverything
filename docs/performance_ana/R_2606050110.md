### 串行执行 GCD 堆积模式

查询按顺序执行，GCD 延迟存在累积效应：
- 查询 1-8：`x`→`.pdf`→`main.cpp`→...→`abc...`——前 8 个查询累积 GCD 等待。

- 查询 12-16：`dm:today`→...→`verylongquery`——**GCD 释放后恢复正常**。

**模式**：中间位置的查询受 GCD 堆积影响最大；首尾查询相对正常。

## 6. 问题清单

### High：GCD dispatch 延迟——串行执行堆积

- `MacEverything` GCD=1,910ms，`test` GCD=1,262ms——纯调度延迟。
- **原因**：查询串行执行+flush I/O 占用 GCD 线程→中间位置查询堆积最多延迟。
- **这是当前架构的固有问题**——不是突发性故障。

### High：Phase2 I/O（page cache 部分失效）

- `content:import` phase2=1,764ms，`path:/Users` phase2=1,640ms。
- R115 同样的查询仅 55-58ms——**page cache 状态是决定性因素**。
- **当前 tombstone 22.63%→索引文件 7.43M 行→内存压力增大→page cache 无法完全覆盖**。

### Medium（收敛中）：Compaction 即将触发

- 当前 22.63%，按 9,663/min 增速约 18 分钟触发。
- **compaction 后**：
  1. tombstone 归零→文件从 7.43M 缩至 ~5.75M 行（↓23%）
  2. flush rewrite 时间从 3-11s 降至 1-3s
  3. lockWait 归零
  4. page cache 需重新预热（短暂退化后恢复）
- **预计 ~01:28 触发 compaction，~01:55 完成，~02:00 性能开始恢复。**

### 正面：lockWait 已降至可接受水平

- Max 97.8ms——比 R116(763ms)、R117(1,567ms) 大幅改善。
- **事件流减速的直接收益**——WAL 持锁时间缩短。

## 7. 优化建议

### P0：Compaction 后的 page cache 预热

- Compaction 完成后主动预热新索引文件：`posix_fadvise(POSIX_FADV_WILLNEED)` 或 `mmap` + `madvise(MADV_WILLNEED)`。
- **预期收益**：避免 compaction 后 R104-R106 的冷启动退化。

### P1：GCD 队列优先级隔离（一贯建议）

- 查询使用 `QOS_CLASS_USER_INTERACTIVE`，flush 使用 `QOS_CLASS_UTILITY`。
- **消除 flush rewrite 对查询调度的影响**——即使 flush 在运行，查询也不等待。

### P1：降低 Compaction 阈值至 15%

- 系统在 17-22% 区间运行了 1 小时+——全程"亚健康"。
- 15% 阈值可将退化窗口从 ~1.5 小时缩短至 ~20 分钟。

### P2：HTTP 并发查询处理

- 当前串行执行导致 GCD 堆积——中间位置查询最多等待 2 秒。
- **方案**：每个 HTTP 请求独立提交到 GCD 并发队列。

## 9. 结论

**GCD 延迟为主导瓶颈——7/16 >500ms，P50=342ms，Max=2,189ms。** lockWait 大幅改善至 98ms（R117=1,567ms，↓16 倍）——事件流减速效果显著。tombstone 22.63%（1.68M），增速 ~9,663/min——**按此增速约 18 分钟后（~01:28）触发 COW compaction**。flush rewrite 中位 3.4 秒（改善），但仍占用 GCD 线程导致查询延迟。page cache 部分失效（`content:import`=1,764ms vs R115=58ms）。**系统处于第二次退化-恢复周期的末尾——compaction 即将触发，之后将重置为低 tombstone 状态。** 本次周期（R115→R118）持续约 1.5 小时——与第一次周期（R104→R109 约 1.7 小时）时长相近，验证了 25% 阈值下系统的周期性退化模式。**长期优化方向不变**：降低 compaction 阈值（15%）+ GCD 队列隔离 + compaction 后 page cache 预热。
