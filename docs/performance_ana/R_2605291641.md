**8 轮严格单调递增，无一次下降。** 这是一个被前序报告（含我自己的 R57/R58）遗漏的关键事实。

### 推翻 R58 假设

R58 报告假设"压缩获大量回收工作 → 分批持锁 → 阻塞查询"。但若压缩真在回收 tombstone，R58 之后 tombstone 应**下降**。实际 R58→R59→R60 继续上升（110K→113K→128K）。**结论修正：R58 的锁持有者并非"回收 tombstone 的压缩"。**

| R58 锁持有者候选 | R60 新证据下的判定 |
|------------------|-------------------|
| Tombstone 回收压缩 | **排除**（tombstone 未下降） |
| v6 全量 flush | 排除（FLUSH 计数=1） |
| 文件系统写入风暴（WAL 插入争锁） | **未排除，现为首要候选** |
| 内容索引压缩（ContentIndexPersistence） | 未排除 |

### 修正后的锁事件模型

R60 提供了关键对照：**R60 tombstone 增速 33K/h（高于 R59 的 9K/h），却零锁、性能最佳**。说明：

- 锁事件**不由平均 tombstone 增速决定**；
- R58 锁事件更可能由**集中写入风暴**（短时间内大量文件变更涌入，WAL 插入连续争夺排他锁）引起，而非压缩；
- R60 的 33K/h 均匀分摊在 27 分钟内 → 无瞬时风暴 → 无锁饥饿。

> 诚实声明：现有日志无逐操作记录，无法在"WAL 写入风暴"与"内容索引压缩"之间确证。但 tombstone 单调增长已**排除**"tombstone 回收压缩"。**P1 lock hold duration 日志从"建议"升级为"必需"**——这是唯一能区分剩余两个假设的手段。

## 3. ⚠️ Tombstone 累积失控风险（P0 重新升级）

R53 报告曾将 tombstone compaction"降级"，理由是全盘重建已归零（12.97%→0.70%）。**但全盘重建是一次性事件（由 24.5h 停机的 FSEvents 失败意外触发），并非常规回收机制。** R60 数据显示常规运行中 tombstone 持续累积：

| 指标 | 数值 |
|------|------|
| 重建至今时长 | ~3h39min（13:02→16:41） |
| Tombstone 增量 | +90,903（37K→128K） |
| 平均增速 | **~25K/h** |
| 达到崩溃前 12.97% 比例所需时间 | **约 25-30 小时**（按当前记录数 ~700K tombstone） |

若服务连续运行而无真正的 tombstone 回收机制、无再次全盘重建，**约 1-1.5 天后 tombstone 将回到 R43 崩溃前水平**。届时 flush/查询将再次因高 tombstone 比例承压。

**P0 重新升级：tombstone 在线回收**。不能依赖"停机 → FSEvents 失败 → 全盘重建"这一意外路径来清理 tombstone。
