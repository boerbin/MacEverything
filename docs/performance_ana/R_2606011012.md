## 9. 可能问题定位

### P0-1：runtime reclaim 阀门过高，墓碑在 22% 区间继续积累
- 证据：R1012 末 tomb=1,564,762，ratio=22.23%；`RECLAIM=0`；已知阀门为 25%。
- 影响：删除/更新造成的 tombstone 不被运行期回收，扫描上限与 page working set 持续膨胀。
- 根因：阀门按 25% 触发，对当前 21–22% 的长期高压区间不敏感。

### P0-2：查询读路径与 flush/page fault 仍强耦合在锁内
- 证据：慢项 `lockHeld/total` 约 94–100%；`中文测试` 242.60ms 中 lockHeld=242.57ms。
- 影响：任何 cold page 或全扫抖动都会扩大为持锁延迟，影响并发查询。
- 根因：读路径在共享锁/临界区中完成较重的 slot/page 访问。

### P0-3：string/filter 全扫平台仍高于干净基线
- 证据：`path`/`中文`/`content` 再探地板 149.30 / 177.93 / 126.46ms，仍约为 R841 干净基线 2–3×。
- 影响：普通路径、中文、内容过滤查询的用户感知延迟维持在百毫秒级。
- 根因推断：大 rewrite 后 mmap/index pages 被驱逐，后续查询靠实际负载缓慢 re-fault，恢复速度慢。

### P1：flush 门控压力仍在增长，但本轮从加速转为小幅增加
- 证据：`SKIPFLUSH 25→26`，`FLUSH 1050→1114`，`FLUSH_GE5 118→120`。
- 影响：虽然本轮没有新 query 事故，但 flush 债务仍存在。
- 根因：pending 阈值、flush 触发条件与实际写入/重写速率不匹配。

## 10. 优化建议

1. **下调 tombstone runtime reclaim 阀门：25% → 8–10%**  
   当前 ratio=22.23% 且 `RECLAIM=0`，说明 25% 阀门在实际长期高压区间不可达。先做小步调参并用真实日志验证 rewrite 时长、reclaim 次数、查询 tail 是否下降。

2. **实现读路径无锁快照 / flush 指针交换发布（TOP）**  
   目标不是让每个查询都更快，而是把 page fault、full scan、flush 发布从同一个持锁窗口拆开，避免 `lockHeld≈total` 造成的尾部放大。

3. **对 string/filter 全扫页做 rewrite 后预热或 `madvise(WILLNEED)`**  
   本轮没有新事故但平台仍高，说明自然回暖太慢。预热应聚焦 path/name/content 相关 slot 页，避免复制大表或引入常驻大内存。

4. **增加 flush storm guard：按窗口内 rewrite 密度限速，而不是只看单次 rewrite**  
   之前 R846 的 08:36–08:38 密集簇是平台硬化源头；本轮只有孤立 5–6s rewrite，没有触发新事故。guard 应针对“密集簇”而不是孤立小峰值。

5. **治理 SKIPFLUSH：记录 pending、阈值、跳过原因与下次成功 flush 的间隔**  
   当前 `SKIPFLUSH=26` 仍在涨。需要把“跳过是健康节流还是刷新债务”区分出来，否则只能看到计数增长，无法判断债务大小。

6. **给 full-scan 查询增加尾部预算与分段让出**  
   `path`/`中文`/`content` 仍是百毫秒平台。分段扫描可以降低单次持锁窗口和尾延迟；应避免新增复杂索引，先用分段/预算降低风险。

**资源平衡说明**：以上建议优先是阈值、调度、锁边界、page-state 管理，不建议引入大内存倒排表或重复计算型补丁。预热应使用 OS page hint 或小范围顺序触碰，不复制完整索引；无锁快照的额外内存应限制在 flush 发布期间的短暂版本窗口。

## 11. 结论

🟡 **本轮是“无新查询事故 + 残留平台未清空”**：查询电池和再探没有新增 ≥500ms，R941 的 trigram 209ms 瞬态也未复现；但是 `path`/`中文`/`content` 的再探地板仍为 149.30 / 177.93 / 126.46ms，显著高于 R841 干净基线。日志最新 session 仍 0 warning / 0 error，说明不是功能错误；真正的风险仍是性能治理：墓碑升至 22.23%、`RECLAIM=0`、`FLUSH 1050→1114`、`SKIPFLUSH 25→26`。证据继续指向四个根因级方向：**降低 reclaim 阀门、读写解耦/无锁快照、string/filter 页预热、flush 门控压力治理**。

> **一句话**：R1012 没有新增查询事故，trigram/ext-index 基本健康，但 full-scan 平台仍在 2–3× 干净基线上方，且 tombstone/flush/SKIPFLUSH 继续上行；应继续优先做 P0#2 读写解耦、P0#1 阀门下调、P0#6 页预热与 P0#7 flush 门控治理。
