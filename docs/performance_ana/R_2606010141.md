## 10. P0 优化建议

1. **立即下调 `:159` 比率阀 0.25→8–10%**：墓碑已 20.88%，连续 33 轮运行期 compaction=0；25% 阀门已被「数值层 + 字符串层分别越过 500ms」彻底证明过晚。
2. **读写解耦 / lock-free snapshot flush（本轮升级为最高优先）**：本轮首次直接观测到 dm 查询被相邻 rewrite 簇页态拖到 527ms（再探立即回落 40–84ms）。必须让查询读取稳定快照，而不是被并发 rewrite 页态污染。这是唯一能同时解释 dm 527ms（耦合）的根因项。
3. **storm guard 必须按 rolling flush 簇触发**：01:40–01:43 出现 8 次 2.7–5.7s rewrite 背靠背（间隔仅 30s）。即使其中只有 1 次 ≥5s，簇整体已足以污染查询；应按滚动窗口 flush 簇密度（而非单次时长）触发降频/合并/延后。
4. **full-scan tail guard**：path 电池 374ms、W2 312ms，中文 W1 457ms；`advanced-linear-gcd` 与 pure-filter 字符串路径仍需批处理让步、时间片上限或可中断扫描。
5. **dm 列驻留/页态保护**：dm 在 flush 簇相位被推到 527ms，常态却仅 40–84ms。在 lock-free snapshot 落地前，至少应让 dm 等高频数值列常驻、避免被 rewrite 页态换出。
6. **查询超时/熔断**：数值层与字符串层都已越过 500ms，应保留上层熔断，避免 20.8%+ 墓碑叠加 rewrite 簇时再次产出秒级用户慢查询。

## 11. 结论

- **定性**：🔴 本轮新增 1 条 `dm:today 527ms`，数值层首次越过 500ms，且与 01:40–01:43 密集 rewrite 簇强耦合。
- **三段互补证据**：
  - R_2606010041：风暴（523.6s rewrite）但查询未受害——相位运气。
  - R_2606010111：查询受害（中文 839ms）但无新风暴——字符串 full-scan 解耦绝对尾部。
  - R_2606010141（本轮）：数值查询受害（dm 527ms）且与 flush 簇强耦合——read-write 页态耦合实锤。
- **关键发现**：
  - QueryAdvanced ≥500 从 78→79，新增 01:42:04 dm 527ms。
  - dm 527ms 夹在 01:41:43 与 01:42:14 两次 rewrite 之间；再探脱离该簇立即回到 40–84ms。
  - flush ≥5s 97→98（新增 01:42:46 5664ms，同簇）；≥10s 持平 17。
  - 墓碑 1.442M/20.88%，运行期 compaction/reclaim 仍为 0（第 33 轮）。
- **根因判断**：不可回收墓碑持续撑大扫描边界（字符串解耦尾部）；慢 rewrite 簇制造页态扰动（数值耦合尾部）。两条失效路径在 20.8% 墓碑下都已被实测命中，互为印证同一根因的两面。
- **行动建议**：本轮起将 **lock-free snapshot flush（读写解耦）提升为与比率阀 reclaim 并列的最高优先**；storm guard 必须按 rolling 簇密度触发，full-scan tail guard 与 dm 驻留同步推进。否则 20.8%+ 墓碑叠加密集 rewrite 簇会继续在两条路径上交替产出 ≥500ms 用户慢查询。
