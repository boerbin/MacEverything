## 9. 可能问题定位

### P0-1：Runtime reclaim 阀门仍过高，23% tombstone debt 无法触发回收

证据：

- 本轮最终 `tombstoneRatio=23.15%`。
- 日志段 `COMPACTION=2 / RECLAIM=0`。
- 相比上一轮，recordCount 增加 `23,074`，其中 tombstones 增加 `21,725`，live records 只增加 `1,349`。

根因判断：系统当前允许 20%+ tombstones 长时间存在，导致扫描面和 rewrite 成本持续膨胀；25% 阀门在实际工作负载下太迟。

### P0-2：Full-scan 查询仍在锁内承担 page-access 成本

证据：

- `path:/Users total=285.37ms / phase2=274.68ms / lockHeld=274.68ms`。
- `中文测试 total=283.21ms / phase2=283.04ms / lockHeld=283.19ms`。
- `content:import total=205.53ms / phase2=198.36ms / lockHeld=198.36ms`。
- 这些查询 `candidates=0`，耗时不是候选集处理或排序造成。

根因判断：全槽扫描和相关 page fault/字符串访问仍位于锁持有窗口内。即使本轮未超过 500ms 阈值，一旦 page residency 变差，慢查询会直接放大成锁竞争。

### P0-3：列访问成本差异过大，path/content/中文扫描明显 page-bound

证据：

- `size:>100m` floor `15.84ms / 2.22ns/slot`。
- `content:import` floor `129.81ms / 18.20ns/slot`。
- `path:/Users` floor `177.02ms / 24.82ns/slot`。
- `中文测试` floor `138.57ms / 19.43ns/slot`。

根因判断：同样是 full-slot scan，不同列差异达到 8–11 倍，问题不在 query 长度或调度框架，而在字符串/路径/内容页布局、访问局部性或编码处理。

### P1：dm 列本轮退化

证据：

- `dm:today` floor 从上一轮 `43.63ms` 上升到本轮 `52.31ms`。
- Floor W1/W2 的最低值也在 `62–63ms`，高于上一轮。

根因判断：dm 列可能受同样的 page residency 或列布局扰动影响，但程度低于 path/content/中文。

## 10. 优化建议

### P0：将 runtime reclaim threshold 从 25% 下调到 8–10%，或改为 debt-based 复合触发

- 当前 23.15% tombstone ratio 已经足以扩大扫描和 rewrite 成本，但仍没有 reclaim。
- 建议引入 `ratio + tombstone absolute count + recent rewrite density` 的复合触发，而不是单一 25% 比例阀门。
- 验收标准：`RECLAIM>0`，tombstone ratio 回落到 10% 以下，full-scan ns/slot 不再随 tombstones 单调上行。

### P0：读写解耦，避免锁内 full-scan/page fault

- 查询获取不可变 snapshot 后释放全局锁，flush/rewrite 通过 pointer swap 发布新结构。
- 对 `advanced-linear-gcd` 和 `advanced-pure-filter-soa-gcd` 优先实施，因为它们的 `lockHeld≈phase2≈total` 最明显。
- 验收标准：慢查询中 `lockHeldMs / totalMs` 明显下降；page-cache 尖峰不再等比例扩大锁持有时间。

### P0：建立 rewrite density guard 与 post-rewrite prewarm

- 新增 rewrite 密度护栏：当短窗口内出现多个 ≥5s rewrite 时合并、推迟或降频。
- rewrite 完成后对 path/content/trigram 字符串页做轻量预热，降低首轮查询冷页尖峰。
- 验收标准：`FLUSH_GE5` 增速下降；battery 首轮与 reprobe 的差距收敛。

### P1：定位 path/content/中文列的 page-touch 和字符串访问成本

- 为 full-scan 路径增加列级指标：访问槽数、字符串 dereference 数、跳过数、慢页估计、编码匹配耗时。
- 用 `size` 作为 scan-framework baseline，逐项比较 dm/path/content/中文的额外成本。
- 验收标准：解释并缩小 `2.22ns/slot` 到 `18–25ns/slot` 的差距。

### P1：full-scan tail guard / segmented yielding

- 对 path/content/中文类扫描加入分段预算，避免单次扫描在 page fault 时形成连续长锁占用。
- 该建议不是根治替代品，必须配合读写解耦；否则只是降低尾部尖峰，不会消除锁内慢页访问根因。

## 11. 结论

本轮没有新增 ≥500ms 慢查询日志，trigram/ext-index 路径也未复现上一轮 `README` 冷尖峰；短期查询表面稳定。但 status 和日志显示系统债务继续扩大：`tombstoneRatio=23.15%`、`FLUSH=1412`、`FLUSH_GE5=136`、`RECLAIM=0`。最关键的根因仍是：tombstone reclaim 阀门过高、full-scan/page-access 成本位于锁内、path/content/中文列访问局部性差。建议优先处理 reclaim threshold 和读写解耦，否则随着 tombstone ratio 逼近 25%，下一次 rewrite/page-cache 扰动仍可能重新触发显性慢查询事件。
