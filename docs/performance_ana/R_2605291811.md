## 2. ⚠️ 决定性证据：phase2 由页访问主导，非候选数量

本轮日志同时记录了候选数量，揭示一组关键对照：

| 查询 | candidates | phase2Ms | 每候选耗时 | 解读 |
|------|-----------|----------|-----------|------|
| `main.cpp` | **71** | **1665** | **23.5ms** | 极少候选、极慢——71 条记录散落冷页，每条一次随机磁盘读 |
| `*.swift` | 9,204 | 1666 | 0.18ms | 大量候选、相近耗时——页局部性较好，半顺序读 |
| `.pdf` | 9,890 | 756 | 0.08ms | 候选多但部分页已热 |
| `README` | 16,432 | 21 | 0.001ms | 候选最多但**最快**——页全热 |

**`main.cpp`（71 候选）与 `*.swift`（9204 候选）phase2 几乎相同（1665 vs 1666ms），候选数却差 130 倍。** 若 phase2 成本由候选数决定，`main.cpp` 应快 130 倍。事实相反——证明 phase2 成本由**候选记录所在数据页的缓存状态**决定：

- `main.cpp` 的 71 条命中记录散落在全盘各处（`main`/`cpp` 是常见词，匹配文件遍布），每条记录的 SoA 列数据落在不同冷页 → 71 次随机页错误 ≈ 1665ms（每页 ~23ms 冷读延迟）；
- `*.swift` 的 9204 候选页局部性更好（扩展名集中），半顺序读摊薄到 0.18ms/候选；
- `README`（16432 候选）页全热 → 21ms。

> 这是 R56/R61/R62 反复观察到的冷缓存现象的**机制级确证**：一条返回 71 结果的查询耗时 1.8 秒，根因不是算法、不是数据规模、不是锁，而是**候选记录数据页未驻留缓存导致的随机磁盘 I/O**。

### R63 核心论证：页常驻方案具体化

`main.cpp` 案例证明 phase2 随机页 I/O 是主瓶颈。建议方案：
1. **SoA 关键列 mlock 常驻**：将记录名/路径/大小等 phase2 必读列锁定内存，杜绝冷读。当前 5.36M 活跃记录，关键列内存占用可估算后常驻；
2. **候选页批量预读**：phase2 开始前对候选记录 ID 对应的 SoA 页发 madvise(WILLNEED)，把 71 次串行随机读转为并行预取；
3. **评估 SoA 行 ID → 页映射的局部性**：`main.cpp` 的 71 候选每条一页是最坏情况，若能按访问频度重排记录，可提升热点局部性。

方案 1（mlock）最直接——它同时根治模式 A 的两种表现（少候选散页 / 多候选半顺序），是比"无锁化"更能根治冷缓存的手段。
