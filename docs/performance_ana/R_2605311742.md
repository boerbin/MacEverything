## 10. P0 优化建议

1. **立即下调 `:159` 比率阀 0.25→8–10%**：墓碑 18.46%，连续 17 轮运行期 compaction=0，且本轮又触发 22.3s rewrite。继续等待只会让下一个主峰更大。

3. **lock-free snapshot flush**：本轮电池贴近 22.3s flush，多个查询在同一秒级窗口被污染；读写锁/页态解耦是减少相位依赖的根因修复。
4. **mlock/madvise dm 列**：dm 再探 5/6 高位，且对抗口径仅 1.04×。约 53MB 成本仍是最小的数值层保护。
5. **查询超时/熔断**：虽然本轮最大 872ms，不如 R_2605311612 的 8.1s，但同一机制可复发，用户层必须有保护。

## 11. 结论

- **定性**：🔴 强风暴再起。17:42 出现 22.3s rewrite，电池和 floor 窗均被污染。
- **分裂**：**51/51** 维持，但对抗 1.04× 再次贴线。
- **关键发现**：
  - 电池三条 trigram ≥500ms 与 17:42:39 flush 主峰贴合；再探迅速回落，证明是相位污染而非 trigram 永久退化。

  - 墓碑 1.234M/18.46%，入墓比 97.4%，数据层继续恶化。
- **根因判断**：不可回收墓碑扩大 rewrite 成本，周期性制造 flush storm；查询延迟是该风暴通过锁/页态耦合传导到读路径的表现。
- **行动建议**：比率阀下调 + storm guard 是 P0；dm mlock 与 lock-free snapshot flush 是降低相位敏感性的必要后续。
