## 4. 服务崩溃分析

日志最后一条记录时间为 10:33:20（`very long query` 完成），之后服务终止。可能原因：

1. **内存压力**: 56 秒的查询可能导致内存累积，触发 macOS OOM killer
2. **看门狗超时**: macOS 可能因服务长时间无响应而终止进程
3. **线程死锁**: 极端锁竞争可能导致 GCD 线程池耗尽
4. **用户手动关闭**: 最后日志之后无 crash 信号，可能是正常退出

**无 WARN/ERROR 日志**——如果是崩溃，没有被捕获的信号。

## 6. 优化建议（⚠️ 紧急升级）

| 优先级 | 项目 | 预期效果 | 紧迫性 |
|--------|------|----------|--------|
| **P0 #1** | **无锁快照刷写** | **消除 7s+ 锁等待和服务崩溃** | **⚠️ 生产阻塞（服务已崩溃）** |
| **P0 #2** | **增量刷写** | 将 flush 从 628 万全量降至 delta | **极其紧急** |
| **P0 #3** | Tombstone compaction | 减少 flush 数据量 30%+ | 紧急 |
| P1 | Flush 持锁时间监控 | 增加 lock hold duration 日志 | 高（诊断用） |
| P1 | CJK trigram/path 索引化 | 消除线性回退 | 中 |
| P2 | Phase2 分段计时 | 优化热点 | 低 |

### 架构级修复方案

当前全量刷写架构在 628 万记录规模下已不可持续：

```
当前: 查询(shared lock) ←竞争→ Flush(exclusive lock, 628万全量写入)
       ↓
     查询阻塞 0-57 秒

目标: 查询(无锁, 快照读) + Flush(后台无锁增量写入)
       ↓
     查询始终 <500ms
```

**推荐实施路径**:
1. **短期**: 无锁快照刷写——将索引数据结构改为 Copy-on-Write，flush 操作在快照上进行，不阻塞查询
2. **中期**: 增量刷写——只写变更的记录（WAL + checkpoint），将单次 flush I/O 从 ~1GB 降至 KB 级别
3. **长期**: Tombstone compaction——定期合并回收，控制总数据量
