### 为什么 `中文测试` 持续恶化而 `path:/Users` 改善

| 查询 | 扫描方式 | 页面分布 | cache 特征 |
|------|---------|---------|-----------|
| `path:/Users` | 前缀匹配 path 字段 | 连续（path 字段紧凑存储） | 一次预热覆盖多轮 |
| `中文测试` | 全名匹配 name 字段 | **分散**（name 嵌入 record 中间） | 单次预热仅覆盖当轮 |

- **path 字段在 SoA 布局中连续存储**——page cache 局部性好。
- **name 字段嵌入在每个 record 结构体中**——需要跳跃式访问→page cache 命中率低。
- **这是 SoA vs AoS 混合布局的固有特性——不是 bug。**

## 9. 结论

**1/16 >500ms——`中文测试`=566ms（连续第二轮超标）。** 其余 15/16 查询 <342ms，P50=37ms，lockWait=0。flush rewrite 1.7-2.6 秒。tombstone 3.92%（228.5K），增速创新低 358/min——系统事件流极度平静。

**`中文测试` 持续超标的根因明确**：linear-gcd 路径扫描嵌入 record 结构体的 name 字段→跳跃式内存访问→page cache 局部性差→深夜 OS 持续回收分散页面→单次查询预热不足以覆盖。**对比 `path:/Users`（SoA 连续存储）从 342ms 改善至 281ms——布局差异是决定性因素。**

**这是数据布局的固有特性，不是性能退化。** 白天持续查询活动将自然预热分散页面。如果未来有需求优化中文搜索性能，可考虑将 name 字段提取为独立 SoA 数组。当前不建议干预——影响范围极小。
