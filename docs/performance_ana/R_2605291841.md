## 执行摘要：迄今最严重的「空闲冷缓存」事件 + 两项结构级根因确证

本轮在 18:11 上一轮之后**空闲约 33 分钟**再发起电池，命中**自重建以来最严重的冷缓存**：`.pdf` 服务端 `total=15749ms`、`*.swift` `total=17928ms`，client 端更高达 21.4s / 22.2s。**关键证据**：`.pdf` 本轮 candidates=9890 与 18:11 轮的 9890 **完全相同**，数据零变化，耗时却从 760ms 暴涨到 15749ms（**20.7×**）——唯一变量是「空闲导致的页驱逐」，这是冷缓存因果的最干净证明。

本轮通过**读源码 + 读 HTTP 响应明细**取得两项**结构级根因确证**，纠正了既往仅看日志 `total` 的盲区：

1. **日志 `total` 系统性低估真实延迟**：日志行（`SearchEngineAdvancedQuery.cpp:1083`）只输出 `total`，而 `total` 仅覆盖 `engine->query()`（返回行号），**不含** HTTP handler 里的结果物化 `forEachRecordWithPath`（为 top-N 每行读 ~9 个 SoA 列/池）。物化在冷缓存下要数秒（本轮 `.pdf` client 21.4s − 日志 15.7s ≈ **5.6s 物化**），却完全不进日志。
2. **HTTP 服务单线程串行**：`handleConnection` 在 `acceptLoop` 中**直接同步调用**（`HttpServer.cpp:201`），无线程池。**一条 21s 冷查询会冻结整个服务 21s**，期间 UI 与其他请求全部阻塞在 TCP backlog。

此外服务端 `timing{}` 明细确证：**phase2 占 total ~99%**（页访问主导）、**lockHeldMs ≈ totalMs**（共享锁被持有整个查询周期，15.7s 冷查询持锁 15.7s → 写者饥饿风险）。Tombstone 越过 3% 至 179,885，增速回升至 ~27.7K/h。

## 2. ⚠️ 结构级根因①：日志 `total` 不含结果物化，系统性低估真实延迟

`handleSearch`（`HttpServer.cpp:386-408`）的计时结构：

```cpp
auto start = steady_clock::now();
auto indices = engine->query(keyword, limit, useTrigram, timing); // timing.totalMs 在此内部测完 → 即日志的 total=
engine->forEachRecordWithPath(indices, [&](...) {                 // 结果物化：为 top-N 每行读 SoA 列 + 路径池
    fullPath = makeFullPath(dirPath, r.name); ... });             // ↑ 此段在 total 之外
double ms = (now - start);                                        // queryTimeMs = total + 物化，仅进 HTTP 响应，不进日志
```

`forEachRecordWithPath`（`SearchEngine.h:297`）对 top-N 每行读 **~9 个独立数组/池**：`pathIndices_[idx]`→`pathPool_`、`origNamePool_[idx]`、`types_/sizes_/modTimes_/inodes_/devIds_[idx]`。20 条结果、行号散落 → 最多 ~180 次随机页触碰，**冷态下耗数秒，却完全不入日志**。

**服务端响应 `timing{}` 实测（本轮回暖后捕获，证明结构而非冷态数值）**：

| 查询 | queryTimeMs（含物化） | totalMs（=日志） | phase2Ms | lockHeldMs | trigramMs | 物化差 |
|------|---------------------|-----------------|----------|-----------|-----------|--------|
| `.pdf` | 455.07 | 437.77 | **436.49** | 437.68 | 0.87 | +17.3ms |
| `main.cpp` | 39.32 | 27.82 | 19.75 | 27.80 | 8.04 | +11.5ms |
| `*.swift` | 155.47 | 152.64 | **149.28** | 152.57 | 3.28 | +2.8ms |

- **`queryTimeMs > totalMs` 恒成立**：物化是真实、结构性的额外成本。暖态仅差几~十几 ms；**冷态成倍放大**——本轮 `.pdf` client 21.4s − 日志 15.7s ≈ **5.6s 纯物化**。
- **既往报告（含 R63）仅分析日志 `total`，完全遗漏物化成本**，故低估了用户实际等待。

## 3. ⚠️ 结构级根因②：HTTP 服务单线程串行，一条冷查询冻结全服务

`acceptLoop`（`HttpServer.cpp:185-201`）：

```cpp
while (running_) {
    int clientFd = ::accept(serverFd_, ...);
    handleConnection(clientFd);   // ← 在 accept 线程内同步执行，无线程池/detach
}
```

只有单个 `acceptThread_`，`handleConnection` 同步阻塞 accept 循环。**含义**：`.pdf` 这条 client 端 21.4s 的冷查询执行期间，accept 循环被占满，**任何其他请求（UI 搜索、状态轮询）都堆在 TCP backlog 里等满 21 秒**。冷缓存的「单点慢」因此放大为「全服务冻结」——用户感知为 App 卡死，而非单条查询慢。

> 这解释了 client≫日志 的另一半：串行客户端下，前一条慢查询的「响应投递 + 下一条排队」叠加进后一条的 client 计时（如 `main.cpp` client 15.1s 远超其 `total` 2.4s）。

## 5. phase2 与持锁：服务端明细确证

- **phase2 占 total ~99%**：`.pdf` phase2=436/total=438；`*.swift` phase2=149/total=153。trigram 索引查找极快（0.9~8ms），**瓶颈全在 phase2 的候选 SoA 列评估（页访问）**。
- **lockHeldMs ≈ totalMs**：`.pdf` lockHeld=437.68 vs total=437.77——**共享锁被持有几乎整个查询周期**（确证 [S4629]）。冷态 15.7s 查询即持共享锁 15.7s，期间任何写者（flush/compaction 的独占锁）被阻塞，并令后续读全部排队 → 写者饥饿 + 雪崩风险。
- **lockWaitMs=0**：本轮单客户端无锁竞争，零等待（与近几轮一致）。

## 8. 优化建议（R64 新增 2 项结构级根因）

| 优先级 | 项目 | 状态/依据 |
|--------|------|----------|
| **P0🔥 新** | **日志补全已计算的 timing 明细** | `total/trigram/phase2/lockHeld/queryTimeMs` 字段**均已算出**，仅日志行未输出（`1083`）。零新增计算，根治「分析盲区」 |
| **P0🔥 新** | **HTTP 解耦慢查询（小线程池/超时）** | 单线程 accept 致一条冷查询冻结全服务（`HttpServer.cpp:201`） |
| **P0🔥 升级** | **关键数据页缓存常驻 + 空闲保温** | 本轮坐实需覆盖 **phase2 候选列 + 物化 SoA 列/路径池**；空闲 33min 即驱逐 → 加轻量「空闲保温」周期触碰 |
| **P0🔥** | Tombstone 在线回收 | 越过 3%，12 轮单调，~27.7K/h，~19.5h 触崩溃前水平 |
| **P0🔥** | 查询超时保护 | 本轮 client 21~22s，远超可接受；R58 曾重演 R43 |
| **P0** | 无锁快照 flush（持锁=全程） | lockHeld≈total 确证，冷查询持锁 15.7s 阻塞写者 |
| **P1** | CJK trigram 索引化 | 中文走线性（222ms，本轮尚可） |

### 三项 P0 的低复杂度落地（符合「收益/复杂度」约束）

1. **日志补全（最低成本最高价值）**：在 `SearchEngineAdvancedQuery.cpp:1083` 的 `LOG_INFO` 追加 `phase2/trigram/lockHeld`；并在 `handleSearch` 物化后补一行 `queryTimeMs`（含物化）。字段已存在，仅打印 → 后续报告不再盲。
2. **空闲保温（根治空闲冷）**：复用现有半小时自检思路，加一个 ~5–10min 的轻量 keep-warm 任务，顺序触碰热点 SoA 页（name/path/size 池）。**不增内存**（保持同一批常驻页不被驱逐），直接消除 16:09 / 18:44 这类空闲冷尖峰。比全量 mlock 复杂度低、内存中性。
3. **HTTP 解耦**：最小改动为「2–4 线程的固定 worker pool + 查询超时」，避免单条慢查询冻结全服务。需权衡：勿引入完整异步框架（复杂度失衡）；固定小池即可。
