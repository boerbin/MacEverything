## 6. 问题清单

### Medium：lockWait 首次出现——flush rewrite 与查询锁竞争

- 6/16 查询出现 lockWait（最高 43ms）。
- **根因**：flush rewrite 时间增加到 4.3 秒 → 锁持有窗口扩大 → 查询命中概率增加。
- **影响**：lockWait 43ms 本身不严重，但如果 rewrite 时间继续增加（白天高峰期），可能出现更长等待。
- **缓解方向**：
  - 短期：可接受——43ms lockWait 对用户体验影响极小。
  - 长期：降低 compaction 阈值（减少记录数）→ 减少 rewrite 时间 → 减少锁竞争。

### Medium：page cache 大面积退化——白天进程竞争

- `path:/Users`=888ms（R129=437ms，↑2x）。
- `content:import`=525ms（R129=315ms，↑67%）。
- **根因**：白天活动恢复 → 其他进程（Finder、Spotlight、IDE、浏览器）竞争物理内存 → page cache 被大面积回收。
- **自然恢复**：白天持续查询活动将逐步预热关键页面。
- **当前属于正常的日夜周期变化——不是 bug。**

### 正面：trigram 路径仍然可用

- 6/16 查询 <50ms——trigram 引擎核心仍然快速。
- lockWait 对大多数查询影响 <50ms——用户可感知但不严重。

## 7. 优化建议

### P1：降低 Compaction 阈值至 15%（优先级提升）

- 按当前 1,356/min 增速，15% 仅需 ~7 小时（中午前后触发）。
- **compaction 减少记录数 → flush rewrite 时间缩短 → lockWait 减少。**
- **当前 4.67% → 白天高峰期增速可能更快 → 实际到达时间可能更短。**
- **这是减少 lockWait 的最有效手段——不需要代码变更。**

### P2：监控 flush rewrite 趋势

- 如果 rewrite 持续 >5 秒，考虑：
  - 增加 flush 间隔（当前 30 秒）——减少频率但每次数据量更大（需权衡）。
  - 或优化 rewrite 路径——减少 I/O 操作。
- **当前 4.3 秒仍在可接受范围——观察为主。**

### P3：lockWait 如果持续恶化

- 考虑将 flush rewrite 改为 COW（copy-on-write）方式——rewrite 期间不持有读锁。
- **当前 43ms 不值得为此做架构变更——仅当 lockWait >200ms 时再考虑。**

## 8. 下一轮重点

## 9. 结论

**2/16 >500ms（`path:/Users`=888ms, `content:import`=525ms），lockWait 首次出现（max=43ms，6/16 查询受影响）。** 这是白天活动恢复的正常表现——事件流加速至 1,356/min（↑3.1x），flush rewrite 达到 4.3 秒峰值，同时 page cache 被白天进程大面积竞争。

**根因链清晰**：白天活动 → 事件流加速 → flush 数据量增大 → rewrite 4.3s → 锁持有窗口扩大 → lockWait 出现 + page cache 被竞争 → 全表扫描退化。**这不是系统退化，而是白天负载的正常表现。**

**P1 建议：降低 compaction 阈值至 15%**——按当前增速 ~7 小时可触发，compaction 后记录数减少 → rewrite 时间缩短 → lockWait 自然消除。tombstone 4.67%（282K），距 15% 约 7 小时，距 25% 约 14 小时。
