## 6. 问题清单

### P0：tombstone 突破 900k 且继续上行

- 证据：tombstone=905,757（14.57%），较上一轮增加 6,793。
- 影响：无效记录比例继续升高，会放大扫描成本、索引重写成本与 compaction 压力。
- 判断：即使本轮前台延迟回落，后台数据形态仍在恶化，说明前台改善更可能来自瞬时 page-cache/系统状态，而不是根因解除。

### P0：new session 内 flush 已累积到 26 次且无退避

- 证据：`FLUSH=26`，较上一轮 +6；`SKIPFLUSH=0`；session 最大 flush total=6164ms，新增 13:48 的 4396ms flush。
- 影响：完整重写继续制造 I/O 与 page-cache 干扰，可能在不同采样点放大 trigram 与 scan/filter 尾部。
- 判断：flush 频率呈稳定累积，尚未看到对 3-6s rewrite 的保护机制。

### P0：linear-gcd 仍是最高前台尾部

- 证据：`path:/Users`=356.1ms，phase2=344.8ms；`中文测试`=306.0ms，phase2=304.9ms。
- 影响：路径和中文查询仍明显高于 300ms，用户可感知；在 tombstone 继续增长或 flush 干扰时仍可能重新接近 500ms。
- 判断：主要耗时仍在 phase2 扫描阶段，lockWait 对这两个最高项没有贡献。

### P1：pure-filter 与 trigram 中位以上波动仍存在

- 证据：`content:import`=142.1ms，`hello world`=113.7ms，`abc def ghi jkl mno pqr`=75.5ms，`dm:today`=76.9ms。
- 影响：虽然本轮比 13:47 改善，但多个路径仍停留在 75-150ms 区间，说明 postings、过滤扫描或 page-cache 状态仍会影响中位以上查询。

### P1：出现一次轻微 lockWait

- 证据：`ext:cpp` lockWait=5.9ms，其他查询 lockWait=0.0ms。
- 影响：单次 5.9ms 不构成主要瓶颈，但这是近期报告中少见的非零 lockWait，应观察是否扩散到更多查询或更高等待。

## 7. 优化建议

### P0：立即提前或分段 compaction

- 以 tombstone 率 14%+ 或绝对 tombstone 900k+ 作为明确触发信号，不再等待更高阈值。
- 结合 segment tombstone 率和 flush rewrite 成本触发局部 compaction。
- 优先处理 tombstone 密集 segment，避免 scan/filter 路径继续扫描大量无效记录。
- 验收：tombstone 率从 14.57% 回落，`path:/Users`、`中文测试`、`content:import` 稳定 <200ms。

### P0：flush 改为增量/COW 页写入

- 将 stable segment 与 delta segment 分离，常规 flush 只追加或替换小段 delta。
- 大段合并放到后台低优先级任务，不与前台查询争抢热页或持锁窗口。
- 验收：常规 flush total <200ms，新 session 不再出现 3-6s 级完整 rewrite。

### P0：增加 flush I/O 压力退避和前台保护

- 当最近 flush 超过阈值时，提高下一次 flush 间隔、降低 batch 频率，或前台查询活跃时推迟大 flush。
- 持久化线程使用低 QoS，并评估大顺序写的 `F_NOCACHE`/同类策略，减少对搜索热页的冲刷。
- 验收：`SKIPFLUSH` 不再长期为 0，3-6s flush 后不再出现 300ms+ linear-gcd 尾部。

### P0：为 advanced-linear-gcd 与 pure-filter 增加轻量剪枝

- 对中文、路径、content/filter 类查询记录扫描记录数、tombstone 跳过数和 segment 分布。
- 评估轻量字符 n-gram、路径分段索引、预过滤位图或 segment-level skip list，以减少无结果或低选择性查询的全量扫描。
- 要求保持内存增长可控，优先使用压缩或按需结构，不引入大常驻索引。
- 验收：`path:/Users` 与 `中文测试` 不再在 300ms+ 区间摆动，`content:import` 稳定低于 200ms。

### P1：细分 trigram/postings 路径

- 对 `advanced-trigram` 记录 postings 读取、候选交并、候选评分、路径加载、结果组装、page-cache miss 近似指标。
- 重点解释 `hello world`、`abc def ghi jkl mno pqr` 在 75-150ms 区间波动的成本来源。
- 验收：trigram 查询在 flush 后仍稳定 <100ms，或至少能解释每个阶段的成本。

### P1：持续观测 lockWait

- 记录每个查询路径的 lockWait 分位数，而不是只看单次值。
- 如果 lockWait 出现在 linear-gcd 或 pure-filter 尾部，应检查 flush、compaction、index swap 与查询共享锁的重叠窗口。
- 验收：lockWait max 长期回到 0ms，或能定位到具体后台任务窗口。

## 9. 结论

**本轮前台性能较 13:47 明显恢复：0/16 >500ms，Max=356.1ms，P50≈32.5ms，P90≈142.1ms。** 但最高项仍是 `path:/Users` 与 `中文测试` 这类 linear-gcd 查询，耗时几乎全部来自 phase2 扫描；`content:import` 与 `hello world` 仍在 100ms+ 区间。

**后台根因没有改善：tombstone=905,757（14.57%）已突破 900k，新 session `FLUSH=26`，最大 flush total=6164ms，新增 4396ms flush，且 `SKIPFLUSH=0`。** 下一步仍应优先推进提前/分段 compaction、增量/COW flush、flush 前台保护/退避、advanced-linear-gcd/pure-filter 剪枝，并补充 trigram 与 lockWait 分阶段观测。
