## 6. 问题清单

### Medium：page cache 冷却导致 `.pdf`=834ms

- **现象**：首个大候选量 trigram 查询 phase2=790ms（lockWait=0）。
- **根因**：18 小时无索引读取 → page cache 被系统回收 → 首次读取是磁盘 I/O。
- **影响**：仅影响冷启动后的前几个查询；后续查询在 battery 中已自行预热。
- **非 bug**——操作系统正常的内存回收行为。
- **可改进方向**：定期 prefetch 索引文件或 mlock 关键页面。

### Low：tombstone 17.22% 持续堆积

- **当前**：1,059,401 tombstone（17.22%）。
- **距 25% compaction**：~9.4 小时（~明天 02:00）。
- **非紧急**——compaction 会自然触发并清理。
- **注意**：上次 compaction 曾导致崩溃（R138 发现），需关注下一次触发。

### Positive：系统稳定性极佳

- 18 小时无 WARN/ERROR。
- 无崩溃、无异常。
- lockWait 几乎为零（max=2.6ms，可忽略）。
- flush rewrite 极快（838ms——因数据量极小）。

## 7. 优化建议

### P0：排查 compaction rewrite 崩溃根因（持续建议）

- 下次 compaction 预计 ~9.4 小时后触发。
- R138 的崩溃根因仍未确认——需要在触发前完成排查或增加防护。

### P1：索引文件 page cache 预热（新增建议）

- **问题**：长时间无查询 → page cache 冷却 → 首次查询 >500ms。
- **方案选项**：
  1. **轻量 prefetch**：定期（如每 5 分钟）对索引文件执行 `posix_fadvise(POSIX_FADV_WILLNEED)` 或 `madvise(MADV_WILLNEED)`——保持 page cache 不被回收。
  2. **mlock 关键页**：将 trigram postings 的热点页面 mlock 到内存（代价：增加常驻内存）。
  3. **接受现状**：冷启动后第 2-3 个查询即恢复（当前 battery 已验证）。
- **推荐方案 3（接受现状）**：除非用户在冷启动场景下有明确延迟投诉，否则不值得增加复杂度。

### P1：flush rewrite 改为 COW 方式（持续建议）

- 本轮 lockWait≈0，但架构风险仍在——下一次活跃期 flush rewrite 膨胀时 lockWait 将重现。

### P2：降低 compaction 阈值至 15%

- 当前 17.22% 已超 15%——如果阈值为 15% 则早已触发 compaction。
- 更频繁的 compaction 避免 tombstone 过度堆积 → flush rewrite 保持轻量。

## 8. 下一轮重点
