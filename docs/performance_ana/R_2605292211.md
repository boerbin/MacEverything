## 2. 🔧 关键修正：tombstone 对线性路径的延迟税被 R68 高估

### 2.1 R68 的原结论与本轮重读

R68 §3 称：线性/纯过滤扫描上界是 `types_.size()`（含 tombstone），死槽跳过给路径叠加「随比例增长的 O(N) 税」，估 `path:/Users(234ms)` 在 4.19% 时含 ~9.8ms 税、12.97% 时 ~30ms。该估计的隐含假设是**死槽成本 ≈ live 记录的 evalNode 成本**（按比例×总延迟）。重读代码后，此假设**不成立**。

### 2.2 代码实证：死槽是「先廉价跳过、后做昂贵工作」

**纯过滤 SIMD 分支**（`SearchEngineAdvancedQuery.cpp:958-976`）：
```cpp
for (; idx + 16 <= end; idx += 16) {
    uint16_t liveMask = me::simdTypeLive16(typesPtr + idx);   // :962
    if (liveMask == 0) continue;                              // :963 全死16槽整批跳过
    while (liveMask) {                                        // :965 只遍历 live 位
        int bit = __builtin_ctz(liveMask);
        ... evalNode(...) ...                                 // :968 evalNode 只对 live 执行
        liveMask &= liveMask - 1;
    }
}
```
死槽**从不进入 evalNode**——被 liveMask 掩掉。死槽的唯一成本是它那一字节被纳入 `simdTypeLive16` 的 16 字节 load（与 live 槽共享同一条 SIMD 指令）。压缩掉 tombstone 仅减少 4.34% 的 SIMD 迭代次数，节省 ≈ (243,738/16)×~2ns ≈ **0.03ms**。

**全评估分支**（`:987-1006`）：
```cpp
for (size_t idx = start; idx < end; idx++) {
    if (typesPtr[idx] == 0) continue;                  // :992 死槽在串池读取前跳过
    const char* nd = namePool.data(idx); ...           // :993-1001 6 次串池读取（仅 live）
    if (!evalNode(*astPtr, ..., nd,nl,pd,pl,...)) continue;  // :1003 昂贵串比对（仅 live）
}
```
死槽在 `:992` 以「一次字节读 + 比较 + continue」跳过，**早于** 6 次串池读取与 evalNode。代价 ≈3ns/槽。243,738 死槽 ≈ **0.7ms**。

### 2.3 修正后的真实税（亚毫秒级）

| 路径类型 | R68 估计 | R69 代码实证 | 偏差 |
|---------|---------|-------------|------|
| 全评估线性（path/中文） | ~9.8ms（按比例×总延迟） | **~0.7ms**（243K 死槽×~3ns 跳过） | 高估 ~14× |
| 纯过滤 SIMD（content/size/dm） | （同上推断） | **~0.03ms**（少 4.34% SIMD 迭代） | 高估 ~300× |

> **结论修正**：tombstone 对线性/纯过滤**查询延迟**的直接税是亚毫秒级，不随比例显著增长。R68 把死槽当作「与 live 等成本的 evalNode」按比例估算，因而高估约 10–300×。**这不影响 tombstone 的 P0 地位，但改变其论证依据**：tombstone 的真实代价是 ①SoA 数组内存膨胀（6 列永不收缩）②R43 在 12.97% 的崩溃风险——而非线性查询延迟。**R68 耦合的「修 flush 顺序 = 加速线性查询」红利被证伪，两个 P0（tombstone 回收 / 线性路径优化）应解耦。**
