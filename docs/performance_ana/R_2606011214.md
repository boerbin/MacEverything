## 9. 可能问题定位

### P0-1：Runtime reclaim 阀值过高导致 tombstone debt 长期不释放

证据：

- 本轮 tombstone ratio 已到 `22.92%`。
- 日志段 `COMPACTION=2` 但 `RECLAIM=0`。
- 相比 R_2606011143，tombstones 增加 `24,162`，live records 仅增加 `783`。

根因判断：当前 runtime reclaim valve 接近 25%，而工作负载长期停留在 22–23% 区间。这个区间已经足以扩大扫描面和 rewrite 成本，但还不足以触发 reclaim，因此系统会持续积累结构性债务。

### P0-2：查询读路径仍在锁内承担 page-access / full-slot 扫描成本

证据：

- `path:/Users total=194.63 / phase2=189.60 / lockHeld=189.60`。
- `content:import total=193.90 / phase2=184.29 / lockHeld=184.29`。
- `中文测试 total=313.08 / phase2=282.77 / lockHeld=283.30`。
- 这些路径 `candidates=0`，说明耗时不是结果排序或候选展开造成，而是全槽访问本身。

根因判断：读路径在锁持有区间执行完整 page/slot 访问；当 page residency 差或 rewrite 干扰发生时，查询尾延迟直接变成锁持有时间，影响并发读写。

### P0-3：rewrite 密度继续升高，存在 page-cache 扰动风险

证据：

- 本轮 `FLUSH_GE5` 从 128 增至 134，`FLUSH_GE10` 从 21 增至 22。
- 近期新增多个中长 rewrite：7.6s、7.3s、5.1s、5.3s、5.7s、17.3s。
- 初始 battery 的 `README=401.80ms` 随后 reprobe 到 `1.78ms`，符合“短时 page/cache 扰动后恢复”的形态。

根因判断：rewrite 与 mmap/page-cache 热页存在竞争。即使没有新增 ≥500ms 慢查询日志，401ms 的 trigram 尖峰说明索引页或字符串页仍会被短时扰动。

### P1：不同列的 full-scan floor 差异过大

证据：

- `size:>100m` floor `21.53ms / 3.03ns/slot`。
- `dm:today` floor `43.63ms / 6.14ns/slot`。
- `content:import` floor `166.70ms / 23.45ns/slot`。
- `path:/Users` floor `166.93ms / 23.48ns/slot`。
- `中文测试` floor `200.69ms / 28.23ns/slot`。

根因判断：扫描框架本身不是主因；列布局、字符串访问、路径/内容页局部性、编码处理和 page residency 差异才是主因。

## 10. 优化建议

### P0：把 runtime reclaim 阀值从 25% 下调到 8–10%，并增加 debt-based 触发

- 当前 22.92% tombstone ratio 已经对扫描面和 rewrite 成本产生影响，但仍不触发 reclaim。
- 建议将 runtime reclaim threshold 降至 8–10%，或引入 `tombstones absolute count + ratio + rewrite density` 的复合阀门。
- 验收标准：`RECLAIM>0`，tombstone ratio 回落到 10% 以下，full-scan ns/slot 不再随 recordCount/tombstones 单调抬升。

### P0：读写解耦，缩短查询锁持有窗口

- 将查询所需结构发布为不可变 snapshot，flush/rewrite 通过 pointer swap 发布新版本。
- 查询阶段只获取快照引用，不在锁内执行 page fault 风险较高的全槽扫描。
- 验收标准：慢查询的 `lockHeldMs / totalMs` 明显下降；full-scan 尖峰不再等比例扩大锁持有时间。

### P0：为 rewrite 增加密度护栏与 post-rewrite prewarm

- 对短时间内连续 ≥5s rewrite 进行节流或合并，避免 page-cache 被连续大写入扰动。
- 对 trigram/path/content 字符串页在 rewrite 后执行轻量预热，或用 `madvise(WILLNEED)` 提示即将访问的 mmap 区域。
- 验收标准：trigram 类 `README/.pdf/MacEverything` 初始 battery 尖峰减少，reprobe 与首轮差距缩小。

### P1：拆分 full-scan tail guard，避免单次扫描无让步地占用 CPU/page fault 窗口

- 对 `advanced-linear-gcd` 与 `advanced-pure-filter-soa-gcd` 加入分段预算与让步机制。
- 保持单次查询语义不变，但避免 path/content/中文扫描在 page fault 时形成长时间连续锁占用。
- 验收标准：`path:/Users`、`中文测试` 的 p95/p99 降低，且 `lockHeldMs` 不再接近 `totalMs`。

### P1：定位 dm/path/content/中文列的内存布局差异

- 用列级计数器记录每类 filter 的 page touches、string dereference 数、miss/slow-page 估计。
- 优先比较 `size` 与 `path/content/中文`，因为它们同样扫描全量槽位但 ns/slot 相差 7–9 倍。
- 验收标准：能解释 `size≈3ns/slot` 与 `中文≈28ns/slot` 的差距，并将 path/content/中文 floor 拉近到 dm 级别。

## 11. 结论

本轮没有新增日志记录的 ≥500ms 慢查询，trigram/ext-index 的初始尖峰也能通过 reprobe 证明是瞬态；但系统并不健康。核心风险正在从“显性的 query incident”转为“持续累积的 storage debt + full-scan page-access floor”。`tombstoneRatio=22.92%`、`RECLAIM=0`、`FLUSH_GE5=134` 和 full-scan `166–200ms` floor 共同说明：若不降低 reclaim 阀值并解耦读写锁，下一轮大 rewrite 或 page-cache 扰动仍可能重新放大成 ≥500ms 查询事件。
